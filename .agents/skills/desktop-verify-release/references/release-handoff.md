# 検証結果と手順の記入観点

配布物を作成・検証して渡すときに使う。既存の成果物記録があればその形式を使う。

## 成果物の対応

- 対象リポジトリ・ブランチ・コミットと、未コミット差分の有無。
- ビルド入力の固定方法、種別、版、OS・CPU、作成日時とタイムゾーン。
- ファイルの場所、ハッシュ、署名・公証の状態、同梱物の照合範囲。

| 検証 | 対象OS・環境 | 実行した範囲 | 結果 | 未実施・除外の理由 |
|---|---|---|---|---|

テスト件数だけで品質や全件成功を表現しない。
文書・整合性、単体、統合、ブラウザー、実アプリ、実モデル、実機、インストールを必要に応じて区別する。

## ローカル検証の手順

該当する項目だけを具体的な成果物に合わせて書く。

1. 必要ならデータを退避し、稼働中アプリを仕様どおり終了する。
2. 検証に必要な信頼登録や権限操作を、実行するユーザーとともに示す。
3. 既存版との版・識別子の関係を確認して導入する。
4. 起動、権限、主要操作の一巡、保存、終了、再起動、更新時の保持を確認する。保存形式変更がある場合は、旧形式からの初回起動移行、完了後の通常利用、次回起動での変換スキップも確認する。
5. 不具合時の診断の取得先と、利用者に渡してほしい情報を示す。
6. 今回の一時アプリ、信頼登録、不要になった検証ファイルを個別に片付ける。

証明書の信頼解除と秘密鍵の削除は別の操作。
継続利用する署名鍵を、検証後の既定手順で削除しない。
公開用パッケージ、個人データ、無関係な登録を消すコマンドを混ぜない。
OSや形式固有のコマンドは、その環境で検証した値か公式資料をもとに具体化する。

## 終了時の状態

commit・push・PR・マージ・公開・インストールは、それぞれ実施済みか区別する。
ローカル検証の成功と、配布サービスの提出・認定・一般公開は別の状態として記載する。

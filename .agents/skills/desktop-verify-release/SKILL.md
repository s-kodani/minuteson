# デスクトップの検証と配布物作成

依頼された変更と配布物を結び付け、どこまで確認したかを再現可能にする。
検証依頼を、本番公開、署名鍵作成、Store提出、利用中アプリの置換の許可へ拡張しない。

## 対象を固定する

リポジトリ、ブランチ、対象コミット、未コミット変更、配布種別、対応OS・CPUを確認する。
同時作業や無関係な変更を保持し、別ブランチや別作業の成果物を混ぜない。
ビルド中にソースが変わり得る場合は、承認範囲内の隔離したスナップショット等で入力を固定する。
未コミット状態から作る場合はコミットSHAだけで一致を主張せず、差分と入力の識別を残す。
不要なブランチ切替やmainへの反映を行わず、依頼された共有先と完了範囲に従う。

## 検証を選ぶ

既存のコマンドとCI定義を読み、変更した境界に必要な検証を実行する。
日常の軽い検証、重い検証、実部品・実機確認、リリース前検証を区別する。
低影響の見た目変更に、実装をなぞるだけのテストや無関係な全件検証を増やさない。
必須検証が失敗・取消・意図せず省略された状態を成功にしない。
フレークの再実行は原因と範囲を確認し、偶然の成功まで無制限に繰り返さない。
OSごとの未実施を明示し、クロスコンパイル・モック・実機の証拠を区別する。

## 配布物を確認する

依頼された形式とプロジェクトの配布手順に従い、必要なアプリ・ヘルパー・ライブラリ・資材を同じ入力から揃える。
利用者へ渡す配布物と、ビルドログ・検証記録・一時資材の置き場所を分ける。整理は依頼された範囲で行い、既存の成果物を無断で削除しない。
名称、識別子、版、CPU、最低OS、同梱パス、設定・データ領域、依存通知を確認する。
QAと通常版の共存が必要なら、データや識別子の分離を確認する。既存の設計を勝手に変更しない。

- ビルド結果と実際の同梱物を照合し、配布物のハッシュと作成元を残す。
- 署名や公証が要求される方式は、その検証結果も確認する。未署名版を署名済みとして渡さない。
- ローカル検証用コピーは原本との一致範囲、署名やメタデータの差を記録する。検証版だけ無断で版を上げない。
- 鍵や証明書は既存の管理方針を優先する。再ビルドのたびに理由なく作り直したり、秘密鍵を成果物へ同梱したりしない。
- 更新、同一版の入替え、ダウングレード、アンインストール時のデータ挙動は採用形式の現在の仕様で確認する。

## 手渡しと公開

成果物、対応するソース、確認結果、未実施、必要な更新操作をまとめる。
検証手順はMarkdown（`.md`）で生成し、配布用ZIPにもMarkdownの手順書を同梱する。
MSIXの署名準備処理が生成する`検証手順.md`を使い、今回の成果物に合わせた追記も同じMarkdownへ反映する。
インストールや実機確認を依頼されていない場合は、再ビルドの成功と区別する。
検証用の信頼登録や一時導入が必要なら、適用先、権限、動作確認、後片付けの手順を用意する。
後片付けは今回作成・登録した対象に限定し、既存の証明書・秘密鍵・データを一括削除しない。
必要なデータ退避は、製品要件とユーザー指定に応じて扱う。

公開・アップロード・PR・pushは、その操作まで許可された場合だけ実行する。
公開の許可があれば、既存の必須条件を満たして完了まで進め、不要な再確認を挟まない。
必要に応じて[検証結果と手順の記入観点](references/release-handoff.md)を使う。

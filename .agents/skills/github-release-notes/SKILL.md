# GitHubリリースノート

MinutesOnの更新内容と必要な対応を、日本語で簡潔に説明する。
GitHub Releasesを本文の正本とし、詳しい検証記録は既存のActions・配布マニフェスト・仕様へのリンクで辿れるようにする。

## 根拠と対象を確認する

- [開発・リリース手順](../../../docs/guides/development-workflow.md)と既存ドラフトを読み、リポジトリ、Release ID、版、公開状態、対象コミットを確認する。
- 比較範囲は前回の公開版の実際のコミットから今回の対象コミットまでとする。最新main、マージ日時、版番号だけで範囲を決めず、未公開・退避済み候補を前回版にしない。
- 差分、含まれるマージ済みPR、現行仕様を照合する。PRタイトルやコミットログを転記するだけで本文を作らず、同じ変更をまとめて説明する。
- 利用者への影響と、準備・テストだけの変更を分ける。CIの成功を実機確認や品質・ライセンス審査の完了としない。性能の数値は測定条件と裏付けがある場合だけ使う。

## 本文を作る

冒頭に今回の要点を1〜2文置き、次の4項目を標準とする。この見出し構成はMinutesOnの規約であり、一般標準として断定しない。

- **主な変更内容**：重要な追加・改善・修正を選び、何ができるようになったか、どの問題が直ったかを書く。
- **ユーザー目線で変わる部分**：今回の更新で**実際に変わる**操作・表示・結果と、利用者が取るべき対応だけを書く。主な変更の繰り返しにせず、変更後にどう使うかを具体化する。**変わらない**操作・画面・データの扱いは書かない。「従来どおり」「同様に利用できる」「スキーマや形式は維持」など、非変化を安心させる一文も入れない。
- **互換ブレーク内容**：差分を確認し、**今回新たに起きる**互換性の破れと、利用者が取るべき移行・回避だけを書く。保存データ、バックアップ、設定、モデル・登録した声、外部連携、対応OS・CPUの変更が互換ブレークに該当する場合に限り記載する。**維持される**こと、**移行不要**であること、旧版との互換のために別途移行が要らないこと、以前からの制約の再掲は書かない。ブレークがなければ見出しごと省略するか、短く「互換ブレークはありません。」程度にとどめる。
- **対応PR**：対象範囲に含まれるPRを説明付きのリンクで列挙する。準備・テストのみのPRはその用途を示し、前回公開版から対象コミットへの比較リンクを添える。

既知の問題、未署名、未確認事項、セキュリティ上の注意など、**利用者の更新判断に直接関係する**事実だけを「注意事項」に書く。移行に必須の注意は互換性欄にも明記し、詳細リンクだけに隠さない。該当しない補助見出しは追加しない。

注意事項に、CI・ビルド・照合の**処理結果**は書かない。Main buildの成功、全件CI・セキュリティ検査の合格、正式配布物の生成・照合完了、ReleaseへのAssets添付、`release-manifest.json`やSBOM・チェックサムの所在など、パイプラインやリリース運用の報告は本文へ入れない。利用者向けに未署名であることや、実機確認・ライセンス審査が未完了であることなど、更新を見送る・追加確認が要る理由になる事実に限る。

ビルドのジョブ数、テスト件数、内部識別子、調査経緯の長い列挙は本文へ持ち込まない。配布資料は版を固定したRelease添付へのリンク、またはAssets内のファイル名案内を優先し、保存期限のあるActions artifactや一時ダウンロードURLを恒久リンクとして使わない。公開前ドラフトに未確定の公開日を付けない。

```markdown
今回の要点を1〜2文で説明する。

## 主な変更内容

- 重要な追加・改善・修正。

## ユーザー目線で変わる部分

- 実際に変わる操作・表示・結果と、必要な対応のみ（変わらない点は書かない）。

## 互換ブレーク内容

- 今回新たに起きる互換性の破れと移行・回避のみ。該当なしなら見出しを省略するか一文で済ませる。

## 注意事項

- 利用者の更新判断に関係する事実のみ（CI・ビルド・照合・Assets添付の報告は書かない）。

## 対応PR

- PRへのリンクと短い説明。
- 準備・テストのPRには、その用途を付記する。

前回公開版から対象コミットへの比較リンク。
```

## 既存ドラフトを編集する

- 編集直前に対象Releaseを再取得し、ドラフト状態、タグ、完全SHA、添付物、本文末尾の`<!-- mon-release:... -->`を確認する。別の候補や公開済みReleaseに変わっていた場合は、既存の更新方針と依頼範囲を確認してから進める。
- 本文だけを更新し、管理コメントは取得した文字列のまま保持する。対象SHA・タグ・添付物、管理コメント内の状態を作り直さない。
- APIのPATCHでは、未公開タグが`untagged-*`へ置き換わる挙動を避けるため、変更しない`tag_name`も送る。タグ保持の扱いは既存の[実装](../../../tools/mon_release.py)の`save_state`を参照し、管理コメントは再エンコードせず保持する。編集画面を使う場合は**Save draft**で保存する。
- 保存後に再取得し、本文、ドラフト状態、タグ、対象SHA、添付物、管理コメントが意図どおりか確認する。並行編集があればその更新を保持し、古い本文で上書きしない。
- 本文編集の依頼は公開・Store送信・再ビルドまで広げない。それらも依頼済みなら、既存の手順と許可範囲に従い、不要な再確認を挟まない。

## 調査元

- [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/)：重要な変更を人向けに整理し、非推奨化・削除・破壊的変更を説明する。
- [GitHubの自動生成リリースノート](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)：PR一覧と比較リンクを収集の補助にし、内容を確認して編集する。
- [GitLabの変更説明の書き方](https://docs.gitlab.com/development/changelog/#writing-good-changelog-entries)：背景を知らない読者にも、変更の結果と利用者への利点が分かる説明にする。
- [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)：採用が確認できる場合は互換性と版番号の関係も確認する。不整合があっても、このskillで版番号を無断変更しない。

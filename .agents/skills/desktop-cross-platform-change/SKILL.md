# デスクトップのOS横断変更

対応対象はプロジェクトが宣言するOS・CPU・配布方式から決める。
Windows・macOS・Linuxの追加対応や、全OSで同じ実装方式を使うことを暗黙に要求しない。

## 変更境界を追う

- 対象の振る舞いを、画面、IPC、共通判定、OSアダプター、外部プロセス、保存、配布物まで必要な範囲で追う。
- 機能対応、資材未準備、実行時エラーを区別する。未対応を成功応答や空の正常結果で覆わない。
- 共通化できる判定と、OS固有のファイル・プロセス・権限・ウィンドウ処理を分ける。
- 小さな不具合の修正に、不要な全体再構成や別プラットフォームの開発を含めない。

## 契約を一緒に変更する

IPCやヘルパーの入出力に、正本となる型・スキーマ・コマンド登録を特定する。
生成処理がある場合は既存コマンドで再生成し、生成物と実装の差分も確認する。
手書きの型、許可、利用者、テストを取り残さない。

データの単位・時刻原点・ID・列挙値・状態を変える場合は、保存、復元、表示、計算、キャッシュの利用箇所を追う。
例えば秒とフレーム、論理IDとファイルの実体、未対応と未準備は別の概念として扱う。
プロトコルの変更は、アプリと同梱ヘルパーの組合せ、実行中ジョブ、更新経路への影響を確認する。
永続データ形式の変更は、通常処理へ旧形式の分岐を増やさず、後日切り離せる専用モジュールで初回起動時に新形式へ移行することを既定とする。
対応OSごとに移行の入口・完了判定・中断再開を確認し、通常処理は新形式だけに統一する。

## OS差異を評価する

該当する境界だけ、採用APIの現在の公式資料と実装で確認する。

- パス表記・大文字小文字・リンク・実体識別・原子的置換・ファイル共有・ロック・同期。
- プロセスの起動引数・コンソール表示・パイプ・子孫の停止・PID再利用。
- 権限の要求方法、アプリ識別子、起動・再表示・終了、フォーカス、DPI、複数モニター。
- ランタイム・ライブラリ探索、CPU／GPU方式、配布物内の配置、署名後の実行。

ホストの環境変数、インストール済みツール、PATHがテスト用資材へ混入しないようにする。
合成入力と実ネイティブ部品を使う検証は、狙う故障が異なるため区別する。

## 検証と受け渡し

共通処理、各OSのビルド、OS固有の実行、配布物の確認を、変更リスクに合わせて選ぶ。
実行できない対象は未検証とし、環境がある担当へ具体的な再現・合格条件を渡す。
OS間の非対称な動作が意図した仕様か、実装不足かを明示する。
必要なら[影響と検証の記録](references/platform-impact.md)を使う。

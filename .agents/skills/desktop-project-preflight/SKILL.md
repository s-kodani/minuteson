# デスクトップ開発の事前設計

技術や機能を増やす前に、利用者が得る結果と開発の終点をそろえる。
特定の言語、フレームワーク、OS、文書形式、保存方式は前提にしない。

## 既存の判断を出発点にする

- 依頼と既存の仕様・設計判断・設定・実装を読み、決定済み、仮定、未確定を分ける。
- 既存アプリの改修では変更する境界だけを調べる。新規開発用の質問や文書を毎回一式要求しない。
- 対象リポジトリ、ブランチ、未コミット変更、検証・成果物作成・共有までの依頼範囲を確認する。既存の許可を引き継ぐ。
- 分かる情報で案を具体化する。後戻りが大きい未決事項だけを質問し、回答待ちでも独立した調査を進める。

## 完成形を観察可能にする

次のうち今回の判断に必要なものを整理する。

- 利用者、主要な作業、完成物の実例、初回と日常の操作の流れ。
- 自動処理と手動編集の境界、設定を全体・対象物・実行直前のどこに置くか。
- 必須機能、後回しにする機能、対象外、既存動作への変更。
- 対応OS・CPU・最低環境・配布経路と、その実行・確認を担う環境や担当。
- 正本、一時物、利用者の原本、再生成できる物、共有資産の所属と寿命。
- 待ち時間・メモリ・容量・品質の目標、測定方法、許容する失敗と復旧方法。
- 開発用キャッシュ・検証資材・配布物の容量予算と保持方針。
- インストール、更新、終了、再起動まで含めた受け入れ条件。

「使いやすい」「高速」「安全」「両OS対応」は、操作例や測定条件へ落とす。
目標、実装済み、測定済み、保証する範囲を混同しない。
以前に省略・対象外と決めた評価を、明示的な変更なしに必須へ戻さない。

## 最小の一巡で前提を確認する

主要な入力から保存・編集・出力・終了・再表示までを通す最小の実装を提案する。
OS API、権限、ネイティブ部品、配布物の成立がリスクなら、その境界を早く実行する。
別OSの型検査やブラウザーモックだけで、ネイティブ動作の成立を判断しない。
UIモックでは通常画面に加え、待機・無効・失敗・取消・復旧の理解しやすさを確認する。

先行検証の結果を、採用・修正・保留の判断に結びつけてから対象を広げる。
検証用のデータ、ダウンロード、端末操作は依頼の範囲と実行権限に合わせる。

## 出力

既存の文書形式に合わせ、目的、決定事項、未確定事項と仮定、対象外、実装順、完了条件を残す。
文書がなければ短い計画で足りる。必要に応じて
[計画の記入観点](references/project-brief.md)を使い、該当しない欄は省く。
仕様変更の理由は設計判断、現行動作は仕様、作業結果はPR等の既存の記録先へ置く。
保存や公開の依頼がなければ、計画のために新しい外部管理先を作らない。

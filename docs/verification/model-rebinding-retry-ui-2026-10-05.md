# 同条件モデル再試行の確認画面

2026年10月5日、文字起こし・話者分離・議事録生成のジョブ欄に、再配置モデルを使う同条件再試行の確認画面を接続した。元の固定条件・途中結果と選択した配置先を表示し、明示確認後にだけ受付処理を呼ぶ。ブラウザーの模擬IPC検証は15ケースが成功した。実モデルとネイティブWebViewによる一連の統合確認は未実施である。正式評価とWindows固有部分の保留、Windows CIの停止は維持する。

## 選択と確認

対象は失敗・取消済みジョブと、復元後のモデル準備待ちにより中断したジョブである。一般の一時停止・中断、上限に達した試行、不正な進捗、未完了の子再試行があるジョブは対象にしない。配置先には同じエンジンの配置済み記録と最新の成功した明示CPU互換性確認が必要で、自動選択やCPU試行の自動起動は行わない。元モデルとの同一性はネイティブ処理が全ファイルと固定条件から検証する。

確認画面は元ジョブID・試行番号・保存済み単位数、固定条件・入力・途中結果のSHA-256、数値条件、トラックごとの人数、用語ヒントの文字数とSHAを表示する。用語本文と文字起こし本文は追加しない。配置先のモデル名・版・エンジン・対象・ライセンス申告、CPU確認操作、全依存ファイルの役割・パス・容量・SHAも表示する。CPUの短い試行を通常設定・GPU・速度・品質の保証として扱わない。

確認と受付の前に既存の編集保存ガードを通す。保存中に親画面がロックされる挙動は、この操作自身が必要とするロックと区別する。保存ガードが操作を開始できなかった場合も明示エラーとし、入力を保持して照合・受付を行わない。現在の設定・人数・用語を、保存済みジョブの条件として取り直すことはない。

## 受付結果と取消

受付前に確認内容と操作UUIDを固定する。応答が未確定の場合も同じ内容とUUIDを保持し、結果確認と明示的な同一操作での受付再試行を区別する。未確定のまま別モデルや新しい操作IDへ自動的に切り替えない。ダイアログを閉じたり会議を切り替えたりしても、同一アプリセッション内では元ジョブから結果確認できる。再起動をまたぐUI操作記録の永続保存は今回の範囲に含めていない。受付済みジョブ自体は従来どおりDBへ保存される。

メイン画面専用の`get_job_model_rebinding_result`を追加した。これは保存済みジョブの受付記録と、対象モデル操作の進行中・取消済み状態を読むだけで、モデル準備の排他取得、推論、ジョブ作成、スケジューラー起動を行わない。進行状態を先に読み、次にDBの受付記録を読むことで、受付記録を読んだ後の確定を「処理終了・受付なし」と誤認する順序を避ける。取消済みトークンでも確定済みの受付記録を確認できる。

取消は処理終了を待ち、遅れて返る取消済みプレビューを表示しない。取消より先に受付が確定していた場合は、その受付記録を表示する。進行中または結果未確定では操作IDを保持し、取消済み・非実行中・受付記録なしを読み取れた場合だけ、新しい確認へ戻る。取消トークンはネイティブの既存の遅延開始防止記録も使う。

モーダル表示時に見出しへフォーカスを移し、閉じると元のボタンへ戻す。処理中はEscape・閉じるで終了扱いにせず、取消要求の専用操作を用意する。デスクトップ幅と390px幅で表示を確認し、長いSHAとパスは折り返し、内容はモーダル内でスクロールできる。

## 検証結果

フロントエンドの状態テスト5件を追加した。3工程の対象判定、成功CPU記録の一致、固定元・配置先・全依存ファイル・人数条件の不一致拒否、進捗した受付記録の由来照合、応答喪失時の操作IDと確認内容の保持を検査する。Rustの既存テストも拡張し、取消要求後の進行中と実際の終了を区別し、配置先ファイルを削除した後も、取消済みトークンで確定結果を読み取れることを確認した。

`app/tests/model-rebinding-browser-fixture.js`で模擬IPCを用意し、Playwright CLIから`app/tests/model-rebinding-browser-check.js`を実行した。成功した15ケースのうち、最初の12ケースは次のとおり。

- 3工程それぞれの明示確認と受付1回。確認だけではジョブを作らず、保存済み単位と高精度・人数条件を表示する。
- 受付済みだが応答喪失、未受付の同一操作再試行、応答喪失後も処理中の3ケース。結果確認ではジョブを増やさず、再受付は同じUUIDと確認内容だけを使う。
- 受付なしで取消が完了する場合、取消より確定が先行する場合、取消済みプレビューが遅れて返る場合の3ケース。実際の終了まで閉じず、確定結果を隠さず、遅延プレビューを復活させない。Escapeとフォーカス復帰も確認する。
- 結果読込失敗と会議切り替え後の再確認、依存ファイル証拠の不一致、編集保存失敗の3ケース。未確定操作を引き継ぎ、不一致と保存失敗では照合後の受付を行わない。

追加した3ケースは、不一致の受付応答を拒否して正しい記録から回復する操作、未確定で受付記録がない操作の明示取消、配置一覧の読込失敗と明示的な再読込である。これらも成功し、合計15ケースを確認した。

最終の`make check`は終了コード0で成功した。Python 65件、フロントエンド82件、Swift 9件、Rust通常461件とAVFoundation製CAF読出し1件が成功した。実モデル等の11件はignored、評価前提の不足は7件の警告として維持した。最後の画面側の小修正後も、フロントエンドのビルドと82件を再確認し、15ケースのブラウザー検証を実行した。

総合検査の結果は[実装状況](../implementation-status.md)を参照する。ブラウザー検証中、ローカルネットワーク制限によるVite開発用WebSocket接続エラーが出たため、画面の更新はページ再読込で確認した。画面操作と模擬IPCの検証結果を、実ネイティブ操作や品質評価の証明には使わない。

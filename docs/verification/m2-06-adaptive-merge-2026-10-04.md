# M2-06 大量項目の分割統合

新規の議事録生成ジョブに、統合入力を省略せず複数の処理単位へ分ける方式を追加した。正式評価とWindows固有部分の保留は維持する。既存の世代1ジョブの固定条件は変更しない。

## 実装と固定条件

- 新規ジョブの生成条件を`schemaVersion: 2`として固定し、従来の抽出計画・二分木の各統合ノード内で分割する。世代1の再開・再試行は元のプロンプト・schema・件数上限・コンテキスト超過時の停止を維持する。既存ジョブを世代2へ読み替えない。
- 左右の完了項目を交互に並べ、種別・担当者・担当話者ID・確定期限・相対期限がすべて一致する群ごとに分割する。各LLM呼出しの入力は固定した`promptBudget`、schemaは32 KiB、入力項目は1,000件以下に制限する。出力に別々の項目を残す余地も恒等結果のJSONバイト数から保守的に見積もる。バイト数は正確なトークン数ではなく、実エンジン側の入力・出力検査も維持する。
- 複数ウィンドウへ分かれた互換群は、最初の結果をウィンドウ間で交互に並べた第2パスでも統合する。同じ分割を繰り返さず別のウィンドウの項目を照合できるが、すべての意味的重複が解消される保証はない。2パスの後も別項目として残った内容は削除しない。
- 単独で入力上限を超える項目と、統合不能なメタデータの単独群はLLMを使わず原項目をそのまま保持する。種別・担当者・期限を推測してそろえたり、長い本文を切り捨てたりしない。空入力もローカル確定する。
- 各パスで元項目IDの全件・一度限りの対応を検査し、根拠発言IDを元項目から継承する。モデルにUUID・引用文・根拠の版・時刻を作らせない。最後の集約も既存の文書・引用・担当者・期限・サイズ検証を通した候補として保存し、現在版と手動下書きは変更しない。

## 途中保存と再開

各分割単位のsystem・prompt・schema・モデル原文・検証済み項目を新規管理ファイルとして登録し、SHA-256をチェックポイントへ保存する。統合ノードが完了するまでは`pending`に完了済みの分割単位を保持する。画面の完了単位数は固定した抽出・統合ノード数であり、LLM呼出し数ではない。

再開・再試行時は固定入力と元ノードから分割と第2パスを再現し、全ファイルのハッシュ、プロンプト、schema、原文から再計算した項目を照合する。検証済みの分割単位は再実行せず、未完了の単位だけやり直す。途中結果の改変・順序違い・重複・異なるノードへの混入は次の推論前に拒否する。

録音開始・一時停止・通常終了は未完了の子プロセスを終了・回収し、既に保存した単位だけを保持する。分割単位のDB保存が失敗した場合はその単位を再開位置に含めない。全分割単位の保存後にノード完了のDB保存が失敗した場合は、保存済み分割単位を失わず再利用する。

文書10,000項目・2 MiB、チェックポイント1 MiB、統合ノードごとの4,096分割単位などの安全上限は維持する。上限やモデル出力の検証違反では省略による成功にせず停止する。親アプリの強制終了時に解析子プロセスを停止する対策は今回の対象外。

## 自動検証

通常テスト11件を追加した（純粋な分割・統合5件、SQLiteと外部プロセス6件）。外部プロセスの通常テストは生成内容を固定した代替CLIであり、実LLMの品質試験ではない。

- 40項目の複数パスで全本文・メタデータ・根拠を保持し、分割順を再現する。
- 最初は別ウィンドウにある同一内容を第2パスで統合できる。
- 互換性のないメタデータと過大な単独項目を原文のまま保持する。重複元ID・未完了結果は拒否する。
- 1,201項目の親結果を旧方式の1,000件上限で切り捨てず、上限内の各単位へ分けて文書化する。
- 統合途中の一時停止・Storage再起動・再開と、失敗後の固定条件再試行で保存済み単位を再利用し、全項目・固定引用・現在版・手動編集を保持する。異なるノードでは同じプロンプトが正当に使われ得るため、重複実行はノード番号とプロンプトハッシュの組で照合する。
- prompt・原文・検証済み項目の改変、再開ノード違い、保存単位の重複を新規推論前に拒否する。
- 分割途中のDB保存失敗とノード完了への切替失敗の双方で、再開位置を進めず保存済み単位だけを再利用する。
- 統合途中の録音優先停止・終了停止で子プロセスを回収し、途中保存情報を保持する。
- 世代1の既存成果物の再開と、従来の過大入力停止を維持する。
- 異なる出力群で同じ元項目IDを重複使用する原文を拒否し、分割処理の位置を進めない。

## 実モデル試行と未達

[アダプターの接続試験](m2-06-llama-adapter-2026-10-04.md)と同じローカルCPU版`llama-completion`、Qwen2.5-0.5B-Instruct Q4_K_Mを使用した。4件の合成決定項目、入力上限2,400、出力2,048、4スレッド、seed 1。私的な会議データは使用していない。

```sh
env MON_LLAMA_COMPLETION=/tmp/mon-llama-integration.dq3nxo/build/bin/llama-completion \
  MON_LLAMA_MODEL=/tmp/mon-llama-integration.dq3nxo/qwen2.5-0.5b-instruct-q4_k_m.gguf \
  cargo test --manifest-path app/src-tauri/Cargo.toml --locked --offline real_llama_bounded_merge -- --ignored --nocapture
```

試行は47.96秒で失敗（終了コード101）。最初のウィンドウの3個の元項目IDを、モデルが3個の出力群すべてへ重複して付けたため、アプリの「統合元の項目IDが重複使用されています」検査で拒否した。生成schemaだけでは群間の重複を防げないことを確認し、対応する通常回帰テストを追加した。原文は保持し、検証を緩めたり、自動修正して採用したりしていない。

合成データと原文・stderr・固定プロンプトは`/private/var/folders/y5/pnx0bxf92l510785mfbxdl_80000gn/T/.tmpk4MNvi/batch-0`に保持した。これは不正結果の拒否を確認する負の試行で、実モデルによる複数ウィンドウ統合の成功・品質・速度達成には算入しない。再現用の実モデル成功経路テストは環境依存のignoredとして残すが、この小型モデルでは未達。モデル選定・実会議の長時間統合と品質は保留中の評価へ残す。

## 全体確認と残件

最終の`make check`は成功。Python 65件、フロントエンド35件、Rust通常141件（環境依存6件はignored）、AVFoundation製CAF読出し1件が通った。正式評価の前提不足7警告は未解消として保持する。macOS開発用`.app`のビルド成功（16.40 MiB）と`codesign --verify --deep --strict`成功も確認。署名はアドホック、公証なしで、ネイティブ画面の一連操作や配布可能性を証明しない。通常の全体チェック成功と、上記の実モデル試行失敗は区別する。

実会議の長時間統合・品質・5分目標・macOS WebView一連操作は未検証で、M2-06全体の完了ではない。Windows CIは保留中のため手動実行のみで、自動実行を再開していない。

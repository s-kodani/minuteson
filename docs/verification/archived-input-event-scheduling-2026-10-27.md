# 終了済み録音の通知取得をイベント中心に変更

2026年10月27日。常時500ミリ秒の全履歴巡回を廃止し、イベント・起動・画面復帰時の取得と60秒の補完巡回へ変更した。通知の受信・実表示・終了確認、音声処理、保存台帳の形式は維持する。

## 実装

- `ArchivedInputScheduler` が全履歴と対象録音の読込みを1つの実行枠で管理する。イベントを250ミリ秒で集約し、読込み中の更新も保持する。全履歴は32件ずつ、後続ページは50ミリ秒後から取得する。巡回終了から60秒後に補完巡回を開始する。
- 通知または未確定操作が残る録音だけを500ミリ秒後から照合する。最大32件の対象指定を公平に巡回し、全履歴のページ取得とも交互に進める。空の確定結果と操作解消後は短間隔取得を停止する。読込み失敗は対象ごとに1・2・4・8・16・32・60秒で再試行する。
- メイン専用IPC `get_archived_recording_input_notice_rows` を追加した。入力は1〜32件の `{meetingId, sessionId}`、応答は既存の `NoticeReply` で `{schemaVersion:1, recordings, missingSessionIds}` を包む。対象の重複・UUID・会議所属・録音終了状態を照合する。全履歴を取得せず、指定IDだけをDBで読む。読込み本体は既存一覧と共通で、復元録音、保存先の同一性、保守権、応答までの経過時間を引き続き検査する。
- 購読登録の完了後に初回取得する。非表示・最小化・保守中は取得と通知操作を止め、復帰時に最新状態を読む。ネイティブの可視性・最小化状態は初回とフォーカス／リサイズ時に確認し、確認失敗時は取得を止めて画面状態を再確認する。購読・タイマーは破棄時に解除し、遅い応答も世代で拒否する。
- 1.5秒の表示鮮度、5秒の受付期限、128件のキャッシュ上限は変更していない。時計が不正になった場合は再起動を案内し、タイマーの過剰実行を止める。100ミリ秒の表示更新は処理がある間だけ動く。
- 自動確認中の待機トーストを廃止した。実際の失敗通知と履歴、再試行操作は維持する。通知が会議一覧の更新より先に到着する場合を考慮し、古い会議一覧に存在しないことだけで通知を除外しない。以前の一覧から実際に消えた会議と、ネイティブの欠落結果を削除の根拠にする。
- 起動時の単一WAV移行を待つ既存の `StartupGate` とネイティブの起動・保存先制限を継続使用する。WAVの配置から通知の保存先を推測しない。通知のJSON履歴と配送台帳が音声整理後も同一バイトで残る回帰検査を追加した。

## 負荷と動作の検証

仮想時計で、初回巡回後59,999ミリ秒は追加読込み0件、60,000ミリ秒で補完巡回1件を確認した。通知のある録音1件と完了済み1件では、後続の照合は未処理1件だけを対象とし、空の確定結果後は停止した。完了済み1,000録音は32ページで巡回を完了し、短間隔の対象指定読込みは0件、保持キャッシュは128件以内だった。これらは呼出し回数とスケジュールの検証であり、実機CPU・消費電力の測定ではない。

# Macでの現行形式の追加復元

現行コードで新規作成した会議をMacの標準画面からバックアップし、元の会議を残して別会議として追加復元した。日本語Markdownと小数秒の再生区間は復元・正常終了・再起動後も一致する。旧会議の変換復元は対象外であり、互換処理を追加していない。

## 破損拒否と再起動

既存の検査用ツールで元バックアップを変更せず破損コピーを作った。本体の末尾1バイトを変更した `payload-digest.monbackup` をMacの標準選択から開くと、「バックアップの管理ファイルハッシュが一致しません」で公開前に拒否された。操作ボタンは受付確認後に復帰した。元の正常なバックアップを選び直して確認画面まで進み、二度目の追加を確定せず「取り消して閉じる」を選んだ。

破損拒否後と取消後の47テーブルの全行は、最初の追加復元完了時と完全一致した。会議数は2件、復元バッチは1件のまま。元バックアップのSHA256も変わっていない。作成した他の3種類の破損コピーはこの実機検査では選択していない。

保存済みのプレビューからCmd＋Qで正常終了し、プロセス終了を確認して再起動した。復元会議の日本語本文と `00:00:00.250000–00:00:04.750000` の区間ボタンを再表示できた。正常終了後・再起動後も47テーブルの全行が一致し、DB整合検査はokだった。再起動後の処理ジョブは0件で、実推論や音声再生は行っていない。最後に復元検証用QAを正常終了し、通常QAへ戻した。

通常QAは会議20件を保持し、以前の検証本文の保存版4・内容ハッシュ `a0395681d40de1417c7ac08b8d7616aa2465b25b29dc7d593894ba4d88cc9ff6` は変わらず、DB整合検査はokだった。会議・音声・モデル本体の削除はない。

## 残対応

今回のMac確認は新規取り込み会議と人間のMarkdown1件による通常追加復元・本体破損拒否・取消・再起動である。実モデルで生成した解析途中状態、異常終了、中断回復、保存先変更・削除の全条件までの実機合格ではない。未準備モデル時に低水準のパスエラーを表示する導線も、今後の簡素化確認で整理する。

旧スキーマ・旧構造化記録などの互換性専用処理の整理は1〜3時間、残るMac異常時統合は1〜2時間、残モデル候補の取得・CPU実行・切替は2〜4時間を見込む。モデル取得では既存の容量承認を超えないよう取得量を照合する。短い実録音の再試験10〜20分と4時間検証には静かな実施時間の合意が必要で、今回の確認に含めない。

実録音・音声再生・OS許可変更・モデル取得・実推論・VoiceOver・CIは今回行っていない。正式評価・10話者・Windowsは保留、VoiceOverは対象外。配布署名・公証・先行試用は外部準備待ちで、開発目標全体は未完了。

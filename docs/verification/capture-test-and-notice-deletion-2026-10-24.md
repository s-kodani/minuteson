# 保存先表示・5秒録音・通知履歴と削除の競合

2026-10-24。既存の作業差分を保持して追補した。インストール済みアプリ、利用者の会議・録音・モデル、OSの入出力設定は変更していない。Bluetoothの音切れと、再現しなくなったPC音声の無音は対象外。

## 保存先と5秒録音

`displayNativePath` で認識できるWindows拡張パスの接頭辞を表示時だけ取り除く。会議・モデル保存先、移動先確認、保持コピーなどに適用した。IPCの値、絶対パスの検証、ファイル操作に使うパスは維持する。合成UIでも、表示から接頭辞がなくなり、元の応答値には残ることを確認した。

Windowsヘルパーはマイク未受信を既に記録していたが、5秒テストの検証側はマイクを必須とし、時刻区間がない場合の `-1` を共通原点の比較に含めていた。マイクとPC音声の両方を任意トラックにし、実際に受信したトラックだけから先頭原点を検査する。取得できた音声が最低1つ必要で、両方未受信は成功にしない。

未受信の明示記録に加え、フレーム・コールバックが0、形式なし、時計・書込み失敗なし、時刻区間が空、CAFが存在しないことを照合する。無音PCMを受信した場合は受信済みのまま扱う。共通5秒枠、原点0、フレーム数、CAFの実体・ハッシュ、所有者と固定UIDの検証は維持し、時計失敗や不正な枠も拒否する。音声の捏造、無音埋め、原点検査の緩和は行わない。

結果表示と個別再生はPC音声のみの結果にも対応する。マイク未受信を明記し、その再生ボタンだけを無効にする。IPCのトラック項目は引き続きnullableで、readyの整合性を「検証済みトラックが1つ以上」に変更した。

## 通知履歴と削除

終了済み録音の0.5秒ごとの確認がページ全体で保持していた共有所有を、会議ごとの処理に狭めた。通知キャッシュも会議ごとの処理ロックを持ち、他会議のファイル同期中にキャッシュ全体のロックを保持しない。

会議全体の削除は既存の会議単位受付を維持する。対象会議を解析側で先に予約し、新しい対象会議の履歴処理を止め、進行中の実I/Oが終了してから保存側の削除予約を取る。関係のない会議の履歴処理を停止しない。音声だけの削除は既存の共有排他を維持し、先に受付を予約してから進行中の履歴処理を待つ。バックアップ・復元・保存先変更の共有排他も維持する。

待機は非同期IPCのblocking workerで行い、Condvar待機中は解析mutexを解放する。5秒で確認できなければ削除を開始せず、再試行可能な拒否を返す。タイムアウト、取消、shutdown、例外で予約を解放する。最終確認で、別会議の復元通知がSQLiteを保持しながら所有を検証する経路とのロック順序の逆転も修正した。解析mutexを保持したままSQLiteを待たず、専用の再現テストで確認した。

履歴APIには `{ paused, value }` の応答と、ページ内の対象会議だけを止める `issue: paused` を追加した。一時停止は空の履歴・保存失敗・受付済みとして扱わず、既存の通知世代や診断を保持する。削除側の受付可否を一般データ操作の可否と分け、実行時には排他を再検査する。実際の待機は所有ID付きイベントで「通知履歴の処理完了を待っています」と表示する。

削除前に対象キャッシュと所有ハンドルを解放し、削除後の遅れた通知応答も無効化する。バックエンドではDB所有のない録音に新しい通知ファイルを作らず、フロントでも削除済み会議を古い応答で復活させない。DBスキーマ、保存済みの削除同意・対象指紋・通知台帳形式は変更していない。

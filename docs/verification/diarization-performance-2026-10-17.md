# 話者分離の高速化候補の実測（2026-10-17）

## 結論

現在のPyannote + ERes2Net baseを保ったCPUの4→8スレッド化が、今回の120秒区間では約14〜16%の短縮となった。話者区間の開始・終了・ラベル38件はすべての成功ケースで完全一致した。Core ML指定は起動できたが、CPUより遅かった。計測ではアプリの設定・ジョブ・保存済み本文を変更していない。後述の設定切り替えは、この比較後に実装した。

## 条件

- Apple M1 Max、論理CPU10、高性能コア8。
- 導入済みsherpa-onnx v1.13.8、Pyannote segmentation 3.0（float）、3D-Speaker ERes2Net base。
- 既存の保存済み16kHzモノラルPCM16 WAVから先頭120秒だけを別ファイルへ切り出した。同じ入力・モデルを使い、ネイティブCLIを一つずつ実行した。
- 人数5固定、クラスタリング閾値0.5、窓移動比率0.1、最短発話・無音補正とも0。人数5は比較条件であり、実際の人数の正解評価ではない。
- 実行前後の時刻差はPythonの単調時計で測定。以下の時間はプロセス起動から終了までで、アプリの音声準備・照合・保存時間は含めない。

区間行を改行で連結したSHA-256は全成功ケースで `2432c67ac9a8ca248e9a51f8d6874aae031ca28e78db5319d048f907dc1b9ca0`。スレッド数・プロバイダー・debug指定の異なる設定ヘッダーまで同じという意味ではない。

4スレッドの内訳は、区間検出2.642秒、特徴量抽出14.886秒、クラスタリング0.000秒、推論全体17.531秒。特徴量計算が約85%を占める。この区間では区間検出だけを軽量化しても、全体の短縮幅は限られる。

## Core MLの途中失敗

最初のCore ML指定は、制限付き実行環境・`TMPDIR=/private/tmp`で作業ディレクトリ作成に失敗し、0.188秒・終了-6となった。推論成功や速度測定に数えない。通常のmacOS実行環境と既存の一時フォルダで再実行した結果が表の40.726秒。Core ML指定で成功したことだけでは、全演算のGPU・ANE実行を証明しない。

## 次の実装で維持する条件

8スレッド化を採用する場合も、新規処理の条件として保存し、管理モデルの設定履歴と一致させる。実行中・保存済みジョブの固定設定を実行時に無断で上書きしない。今回のM1 Max・120秒の結果から、全端末・長時間音声での速度や話者精度を保証しない。

大幅な短縮の候補は特徴量抽出モデルの軽量化。ただしモデル変更では話者対応の比較が必要。公式の[モデル比較](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/models.html)はNeMo TitaNet smallの例を掲載しているが、別の音声・端末の結果であり、日本語会議での品質を裏付けない。

実測ログ・条件・指紋・切り出し音声は、Git対象外の `output/playwright/diarization-performance/` に保存した。計測段階ではモデルの追加取得、会議DBへの書込み、ネイティブアプリの再ビルド・インストールは行っていない。

## モデルと判定条件を維持するCPU設定の切り替え

利用者の「現在のモデル・判定品質をできるだけ維持する」という選択に沿い、ローカルAI設定へ「話者分離のCPU使用量」を追加した。標準4スレッド／多め8スレッドを選び、「CPU使用量を適用」で保存する。既存の別のスレッド数は「現在の設定」として保持する。自動でモデル・全体設定・既存会議を変更するものではない。

使用中の同じ話者モデルに対してだけ、明示したスレッド数の変更を認める。既存のモデル適用処理を使い、確認内容のSHA・設定の版番号・モデル構成の版番号・固定ファイルと互換性証拠を照合する。モデルファイル、クラスタリング閾値、窓移動比率、最短区間補正、もう一方のプロファイルは維持する。スレッド数は新しいモデル構成の版と今後の工程条件へ保存し、開始済みの工程・ジョブの固定設定は上書きしない。CPU設定の変更そのものではダウンロードや推論を開始しない。

同一操作IDの再送は保存結果を読み戻す。保存応答が不明なときは追加適用を止め、「現在の状態を確認」で停止と設定の保存結果を確認する。確認操作から適用を再送しない。録音中・保存先操作中など、既存の設定変更ロックにも従う。

確認状況：

- フロント単体842件、型検査・ビルド成功。使用中のモデル以外のCPU変更、未要求のスレッド数変更、モデルパス・判定条件の同時変更をフロントでも拒否する検査を含む。
- CPU設定の合成ブラウザ4ケース成功：設定・履歴の保存とモデル条件の維持、4スレッドへの戻しと応答喪失の読戻し、保存失敗と明示再試行、ロック・再表示・390px幅。
- 既存の全モデル選択ブラウザ6ケース成功。取得・切り替え・導入済み本体の再利用を含む。
- 変更したRustソースの書式検査と `git diff --check` 成功。
- 最終ソースのネイティブ41件成功。設定の原子的な保存と同一操作の再送、モデル・判定条件と別プロファイルの維持、不正なスレッド数・別モデル・条件改変・取消・競合の拒否、開始済み工程の旧条件維持と新規ジョブの8スレッド固定を含む。既存のモデル適用・再試行・バックアップ・復元も成功。構築191.88秒、実行ラッパー34.96秒（本体28.28秒）。
- 途中の重点検査3件も成功したが、その後に未使用のラッパーを整理したため、最終確認は上記41件とする。途中検査は構築475.23秒、実行ラッパー9.85秒（本体2.72秒）。3件は最終41件にも含まれるため、合算しない。

ブラウザのバックエンドは合成。下記の切り替え用QAには今回の機能を含めた。利用中のアプリの差し替え・再起動は行っていない。

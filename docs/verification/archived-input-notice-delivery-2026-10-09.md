# 終了済み録音の入力通知とネイティブAPI

終了済み録音の入力履歴を、未表示通知の受付・表示・終了を保存するネイティブAPIへ接続した。保存済みの切断・復帰イベントを配送する経路であり、現在の機器接続・音声取得・音声保存を示す経路ではない。この記録はネイティブAPI段階の検証を扱い、後続のメイン画面への接続は[保存後通知の画面接続](archived-input-notices-ui-2026-10-09.md)を参照する。M3-01・M3-08と計画全体は進行中である。

## 録音側と通知側の証拠

ライブ配送台帳の形式版1を、同じ `input-notices.json` の保存後配送形式版2へ移行する。ライブ台帳に保持した実際の取得報告と、録音側の `input-events.json` に保存した取得報告を別々に残す。両者の版番号は別の処理で増えるため、大小だけで新旧を決めない。

入力ごとにイベント番号と取得世代を比較し、重なる履歴の内容を照合して、確認できる新しい履歴を取り込む。片方の入力だけが新しい場合も、もう一方の確認済み履歴を失わない。録音側の保存が遅れた異常終了、取得履歴の欠落・破損でも、通知台帳内の確認済みイベントは保持する。矛盾した履歴は診断を残し、イベントを作り足さない。

保存後台帳は、元の二つの証拠、配送キュー、保持不足と履歴診断、ネイティブの保存版を保持する。配送APIが返すのは通知と保持不足・診断であり、現在の入力状態やライブ報告年齢は返さない。台帳の再生成時には旧画面の受付を無効化し、表示確認済みの通知は再提示しない。

## DB所有と保存先の照合

対象はDBに登録された `saved`・`interrupted`・`failed` の録音だけである。録音中・準備中・停止処理中のセッション、別会議、正準UUIDではないIDを拒否する。ディレクトリの走査で未知の録音を発見したり、音声を再取得・再生したりしない。

一覧APIは録音ID順で32件ずつ返し、続き位置を明示する。画面側は末尾の後に先頭へ戻る必要がある。録音IDは日時順ではなく、前の位置より小さいIDの録音が後から終了する場合がある。

保存先は管理ルートとディレクトリ記述子で固定する。キャッシュした所有者のディレクトリを現在のDB所有先と照合し、差し替え・リンク・所有変更後の書込みや成功応答を拒否する。ある録音の読込み失敗は、その行の固定した診断として返し、別の録音の通知を隠さない。旧録音に履歴も台帳もなければ、新しいファイルを作らない。不正な履歴を空の正常履歴として扱わない。

所有者キャッシュは最大128件で、最後に使われてから最も時間が経った所有者を解放する。IDの大小で解放対象を決めない。再度開く場合は、解放前の画面からの遅い応答を新しい受付世代で拒否する。

## 受付と共有保存所有

一覧取得と受付・表示・終了のAPIはメイン画面専用で、非表示・最小化を新しい通知先にしない。受付者、イベント、受付世代と操作IDを照合し、候補キューの保存確定後だけ成功を返す。応答前にも画面とDB所有を照合する。ファイル同期と一覧の後続処理にかかった時間を受付期限の年齢へ加える。

専用の共有保存所有を実処理の終了まで保持する。録音・解析とは並行できるが、バックアップ・復元・削除・保存先変更とは同時に開始しない。ライブの読取り・受付・表示・終了にも同じ所有を適用し、録音停止後に残った通知保存とデータ操作の競合を防ぐ。通知のファイル同期中にSQLite・録音全体・子プロセスのロックを保持しない。新しい録音開始は通知保存を待たず、アプリ終了は実際の通知ワーカーの終了を期限付きで待つ。

終了・保存先切替で取り消した所有は、終了を取り消しても再利用できない。実処理が終わるまでは共有所有を解放せず、解放後は別の所有者の処理を消さない。

## 残る接続と実機検証

メイン画面の起動時・録音終了後の巡回取得、通知の受付・実表示・終了と未確定応答の読戻し、会議への移動、履歴診断・保持不足の継続表示は[後続の画面接続](archived-input-notices-ui-2026-10-09.md)で追加した。保存先変更・バックアップ・追加復元での取得履歴と配送台帳の扱いは統合確認が必要である。

ネイティブ所有者とDBの再生成検査は製品アプリの再起動試験とは区別する。Mac実機の権限・WebView・実録音・長時間と電源断、実モデルの全経路、配布は別途検証する。正式評価・10話者・Windows固有部分は保留し、Windows CIは停止を維持する。

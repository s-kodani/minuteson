# macOS初回取得の画面・IPC・停止待ち・結果確認

仕様11章の初回取得を、取得定義の明示確認・管理コピーの別確認とともに設定画面へ接続する。[操作手順と定義形式](../model-download-macos.md)を追加した。実配布元・TLS／CDN・実モデル／実機GUI・配布条件の検証を残し、M4-02と計画全体は進行中とする。

## 実装の範囲

main限定の定義確認・取得・操作寿命・履歴一覧・全実体読戻し・管理コピー・由来に結び付いたコピー結果読取を追加する。取得先・コピー先はOS app-data内の固定管理領域で、フロントから任意の保存先を受け付けない。起動受付前の通常IPC拒否を共用する。Windowsの取得は保留応答と未対応の一覧だけを返し、Windows実装・CIを拡張しない。

ファイルシステムを読む／書く準備はInspectorと共有のモデル準備枠を保持する。元の取消フラグと共有枠の取消を合成し、通信子のkill／wait・全照合・同期・コピーDB確定が実際に終了するまで枠を解放しない。進捗通知は操作ID・定義SHA付きで概ね200msに抑制する。全量受信のイベントは完了・準備完了の証拠ではない。

取得定義は入力ファイルもメモリも64KiB、合計容量32GiB。将来のdownload由来配置記録v2が64KiBを超える構成も、通信とディレクトリ作成前に拒否する。容量予算の仮メタデータを物理検査の証拠やDB記録にしない。期待SHA・容量、役割、URL、対象等の既存拒否を維持する。

画面は確認・取得・読戻し・コピー・CPU実行・適用を分ける。定義／配布先／容量／SHA／ライセンスの確認欄を毎回リセットする。TypeScriptでもRustと同順のcanonical JSONをSHA化し、取得定義、元manifest、全検査ファイル、検査SHAを応答へ結び付ける。日本語を含む共通goldenを両言語で独立検査する。取得素材のdirectoryは表示用だけで、コピーの保存先や元フォルダーとしてフロントから再送しない。

応答喪失・不正応答では元の取得／コピーUUIDをプロセス内に保持し、新UUIDで再送しない。同一UUIDの取消を先に送り、取消済みの証拠と実際のactive=falseを確認してから、別の読取UUIDで取得を照合する。コピーは取得ID・定義SHA・検査SHA・配置IDを束ねてDB確定記録を読む。状態読取はDBより先に行い、歴史的なコピー確定を現在の本体利用可能性へ変換しない。

読戻し不能でも、取消と終了・一覧を再確認した上で利用者が明示的に「結果未確定のまま確認を終了」する経路を残す。ファイルは保全し、成功と扱わず自動再取得しない。画面移動後も同一の不明操作を保持し、設定内の既存手動準備・CPU・適用・削除とbusyを共用する。通知を閉じても要対応状態を解消しない。共通モーダルのフォーカス・Escape・実行中の閉鎖拒否を使う。

## 再起動相当の一覧

履歴は最大4,096保持物を走査し、件数超過は省略せずエラーにする。不存在のルートを作らず、リンク・非公開でないルート・未知物を修復・削除しない。正準UUIDの項目にも、途中・要対応を残す。読み取り中のディレクトリ変更を検出する。

「完了記録あり（実体未照合）」は意図と完了マーカーの情報だけ。大きなモデルを一覧表示のために全SHA走査したり、それだけで配置可能な状態にしたりしない。明示的な選択で全実体を読み戻す。配置一覧にもdownloadの取得ID・定義SHAを付け、手動／取得由来の相互関係を検証する。古いフロントfixtureの任意フィールド欠落を許しても、downloadを申告した不正な由来は許さない。旧手動配置記録v1の保存形式は変更しない。

## 検査・失敗・時間

最初のフロント構築はreceiptの検査済み型へのcastで型検査が失敗した。unknownを介した明示castへ修正し、実行時の操作・容量・SHA・未準備検証は維持した。最初の構築全体の時間は個別未計測で、後の成功時間へ混ぜて合格にしない。

最初の重点Rustは33件成功・1件失敗、構築386.62秒・実行区間10.55秒（本体2.56秒）。容量予算のテスト素材に62件の依存ライブラリを指定し、既存の16件上限によって先に拒否された。製品の構成条件を緩めず、18ファイル・有効な階層パスと長いURLで定義予算内／配置記録予算外となる素材へ修正した。失敗はそのまま記録する。

ブラウザの先行検査は、閉じた確認画面にも要対応DOMが残る重複で失敗し、製品表示を修正した（1.78秒）。次は進捗イベント直後のReact描画を待たない検査で失敗した（2.47秒）。DOM読取で25/33の正当な表示を確認し、描画待ちを加えた。利用者が進捗を確認画面内で読めるようにも修正した。16シナリオは5.66秒で成功。その後、旧モデル削除fixtureが新しい読み取り専用一覧IPCを未定義・許可一覧外として扱い回帰が失敗した（2.94秒）。fixtureへ未対応の空一覧と読取許可だけを追加し、製品の検査条件・書込拒否を維持した。10組129ケースの重点回帰は69.61秒で成功。

先行成功を新規件数へ重複加算せず、実モデル・ネイティブGUI・録音・公証の成功にしない。ブラウザのVite HMR WebSocketにはローカルネットワーク制約があり、通常HTTPと合成IPCによる画面検査とは区別する。

修正後の初回重点35件は成功（構築378.73秒・実行区間10.40秒・本体2.75秒）。最初の通常全体は1件失敗（構築55.15秒・実行区間555.48秒）。転送試験の本文・SHAは一致したが接続数が期待2ではなく1だった。試験サーバーには、読み取りタイムアウトによる不完全な要求でもelseの正しい本文を返せる経路があり、原因候補を許さないよう受付と要求先照合を強化した。製品の通信・転送・SHA・時間条件は変更していない。

試験側は4096バイト・2秒・停止フラグ付きでヘッダー終端まで読む。Interrupted／一時的なタイムアウトを扱い、未完・超過・取消は本文を返さない。実接続は数えたまま、`/bin`→`/final`の実際の要求行と2接続、循環の6接続を厳密に確認する。分割・割込み・EOF・容量上限・取消を検査する通常1件を追加した。重点36件はすべて成功（構築58.77秒・実行区間10.32秒・本体2.66秒）。初回失敗の原要求行は保持されていないため、タイムアウトの推測を実測した根本原因と断言しない。固定ソースの最終全件でも成功した。

全ブラウザの先行実行はテーマ通知で停止し、625.54秒で失敗した。snapshotで、テーマの成功通知の再表示ではなく旧設定fixtureの`get_model_download_catalog`未定義による別のエラー通知を確認した。基底の保存／設定fixtureへ未対応の読取応答だけを追加する。製品のテーマや通知の条件は緩めない。

追加のコード確認で、ロック後に確認済みreviewだけを破棄しreceiptを残すと、次のコピー確認が空になる可能性を見つけた。照合済みのメタデータを対で保持し、ロックでは確認画面と同意だけを破棄する。再コピーには新たなチェックとネイティブの全実体再照合が必要なまま。19取得ケースには、ロック後の新たなコピー確認、64KiB超の入力拒否、製品の親パネルでの手動／CPU準備のbusyと同一操作の復旧導線を含む。最終の取得19＋失敗したテーマ6は25ケース、13.28秒ですべて成功。最終全ブラウザも固定ソースで再実行し、成功した。

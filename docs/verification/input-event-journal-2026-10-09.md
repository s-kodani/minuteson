# 録音入力履歴の保存と読出し

通常の会議録音で、マイクとPC音声の切断・復帰履歴を `input-events.json` に保存する。正常停止後もファイルを残し、会議と録音IDを照合した読み取り専用APIから取得できる。保存するのは録音側の遷移履歴であり、通知の表示済み記録ではない。表示確認の永続化と起動時の未表示通知配送は未接続で、M3-01と計画全体は進行中である。

## 保存する範囲

取得方針が状態を変更した時点で、状態と入力ごとの履歴を不変の値として保存処理へ渡す。100msの状態報告や画面の読取りを待たない。初回接続と再取得中の状態も記録するが、切断・復帰イベントを追加する条件は従来と同じである。繰り返し失敗と古い取得結果からイベントを作らない。

各入力の最新64遷移と失われた先頭範囲を保持する。遅い保存処理では書込み中の一件と待機中の一件だけを持ち、待機する状態のコピーを最新へ置き換える。イベント番号は詰め直さず、保持上限を超えた部分は `droppedThrough` に残す。

音声のコールバックと取得方針のロック内では、値を照合して受け渡す。JSON化、ファイル書込みと同期は別の直列キューが担当する。保存失敗で音声取得を止めず、後続の確定に成功すれば保持中の実際の遷移を保存する。停止時は単調時計に基づいて最大3秒待ち、未確定ならmanifestの `inputEventJournalError` に短い診断を残す。この診断の画面表示は残る。

`sealed` は履歴の追記受付を終了したことを表す。PCMの保存完了、OSの取得終了、通知の受付・表示・終了は証明しない。保存が確定する前の強制終了や電源断に対して、全遷移が残るとは保証しない。

## ファイルの所有と確定

通常録音だけが履歴ファイルを作る。正式測定用の時間指定プローブと私有5秒テストは既存の保存先・形式・回収契約を維持する。通常録音の引数では、Foundationが `/private/tmp` などをリンク別名へ書き換えないよう、ネイティブ側が渡したパスを保持する。

履歴の保存先は正規の絶対パスを要し、ルートから各要素をリンク追跡なしで開いて固定する。最初のファイルは排他的に作成し、既存の履歴を引き継いだり上書きしたりしない。ファイルは所有ユーザーの権限0600とし、内容とディレクトリを同期する。

更新は同じ固定ディレクトリ内の排他的な一時ファイルへ書き込み、同期後に原子的に置き換えてディレクトリを同期する。現在のファイルと一時ファイルの実体を照合し、リンク、複数のハードリンク、差替えや変更を検知したら確定を拒否する。失敗時に除去できるのは今回作成した実体と一致する一時ファイルだけである。祖先のパスが差し替えられても新しい領域へ書き込まない。

## 保存履歴の読出し

Rustは元のJSONから重複フィールドも拒否し、形式版、所有ID、上限、必須項目、理由、連続したイベント番号と取得世代を検査する。同じ読取り所有者の中では、版・履歴の巻戻し、重なるイベントの変更、封印後の変更を拒否する。単一リンクの非公開ファイルだけを読み、読取り前後の実体と変更時刻を照合する。

`get_recording_input_history` はメイン画面専用で、任意のパスを受け取らない。DBにある会議・録音IDの組と終了後の状態を確認し、その録音の固定パスだけを読む。別会議、存在しない録音、録音中の対象、リンクを含む管理領域を拒否する。読取りで回収操作・解析・再生・削除を開始しない。

戻り値は所有ID、版、封印状態と両入力の履歴だけである。現在の接続フラグ、報告年齢、通知先、受付者、表示確認を含めない。履歴ファイルだけが存在しても、ライブ入力状態の読取りは成功しない。履歴ファイルの最近の更新を接続の証拠にしない。

録音IDに属する履歴の固定名を削除対象検査の記録に含める。音声だけの削除ではJSONを音声本体として扱わず保持する。未登録の一時ファイルや不正な履歴を、名前だけで回収・削除する経路は追加しない。

## 検証

検証は合成した取得状態、PCMと取得ストリームを使用する。実録音、製品アプリの起動、正式評価、Windows CIは行わない。

Swiftでは、状態報告なしの両入力遷移、停止後の保持、遅い書込み中の400遷移と64件の上限、保存失敗後の確定、古い履歴の拒否、リンクと変更済みファイルの保持、祖先差替え後の固定先を検査する。製品のPC音声取得処理には合成ストリームとPCMを渡し、切断・再取得の履歴が保存へ届くことを確認する。

強制終了の検査では、専用の録音しないXCTest子プロセスだけを起動する。二件の遷移の確定後、三件目の書込みを止めた状態でその子をSIGKILLする。確定済みの二件は残り、未確定の三件目と封印状態は作られない。

Rustでは、厳密な形式、重複項目、保持上限、版・重なる履歴・封印の逆行、リンク・権限・容量、固定ディレクトリ、現在状態との分離を検査する。DB所有の読出しは、録音中と別会議の拒否、終了後と再起動後の同じ履歴、別所有者の拒否と元ファイルの不変を検査する。Swiftが実際に作ったJSONを読む専用検査を `make check-input-journal` と全体検査へ登録する。

全体 `make check` は `/private/tmp/mon-input-journal-full-check1.log` で終了コード0となった。通常Rust1,577件成功・専用59件ignored、Swift115件中113件成功・子プロセス専用2件skip、フロントエンド521件と型検査・ビルド、Python65件と専用連携が成功した。新しい履歴JSONの連携も、Swift生成1件とRust読戻し1件で成功した。

封印後の版変更拒否と音声限定削除の保持検査を最後に補強し、最終ソースの別実行で確認した。通常Rust全体は補強前に構築した検査を使用した。最終の入力状態38件、DB所有の保存履歴1件、音声限定削除の対象検査と実ファイル処理2件、計41件が成功した。ログは `/private/tmp/mon-input-journal-rust-final-focus1.log` で、全体件数へ重複加算しない。画面側のソースは変更せず、模擬IPCブラウザ検査は今回再実行していない。

検査の終了と専用一時領域を使うプロセスがないことを確認し、再生成可能なRust生成物2,256,100KiB、約2.2GiBを削除した。検査ログとソースを保持し、製品targetは38,664KiB、約38MiBのままである。既存releaseの本体と同梱プローブのSHA-256は検査前後で一致した。既存releaseを今回の実装へ更新したという意味ではない。

## 残る接続

画面の受付・表示・終了記録の永続化、録音終了時とアプリ起動時の未表示通知の回収・配送、再起動後の旧受付世代の拒否、保存失敗の画面案内、履歴と保存先変更・バックアップ・削除・復元の統合が残る。Mac実機での通知表示・録音・長時間と電源断の検証は別途必要である。正式評価とWindows固有部分は保留を維持する。

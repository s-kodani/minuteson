# 用語ヒント説明文の文字起こしへの混入調査

2026年10月17日。保存済み会議で「無条件な本文置換ではありません。」が反復する原因を調査した。初回調査は製品コード・保存済み会議・設定を変更せず実施した。ユーザーが承認した修正・追加検証は末尾に記録する。

## 結論

アプリが用語ヒントへ自動付加する説明文を、Whisperが認識本文として生成し、反復している。説明文を含むプロンプトの構成が、この文の混入元である。同じ音声・同じエンジン・同じモデルでプロンプトだけを変える比較により確認した。

用語名だけに短縮すると当該文は消えるが、別の文の反復が残る。今回確認した2区間では、用語ヒント自体を空にした場合に反復が解消した。説明文の削除だけで認識品質が回復するとは判断できない。

## 保存データでの確認

QAのSQLite本体とWALを一時領域へコピーし、コピー側の `quick_check=ok` を確認した。実会議・文字起こしの内部IDは記載しない。

| 現在の本文の時刻 | 問題の文の出現数 | 問題の文を含む行数 |
| --- | ---: | ---: |
| 00:00–02:00 | 61 | 27 |
| 05:58–07:58 | 25 | 13 |
| 合計 | 86 | 40 |

段落結合前の元の認識版では84行に86回。話者分離後も86回、段落結合後も86回であり、後処理で増殖したものではない。現在の全185行で `recognized_text` と `effective_text` が一致している。

直近とそれ以前の文字起こしジョブの両方に同じ86回の混入がある。保存済みのエンジン出力 `result.json` のハッシュをDBと照合し、生の出力から混入していることを確認した。

生のunit 0には62回、unit 3には26回ある。アプリは120秒ごとに前後2秒の文脈を付け、区間中央時刻で採用範囲を決めるため、本文に採用されるのはそれぞれ61回・25回になる。上表は採用後の数である。

終盤の35:58、36:29、36:58、37:28にも、同じ自動説明文に由来する「表記・読みの認識ヒント。」がある。用語名以外の説明も認識結果へ漏れている。

## 混入の経路

`app/src-tauri/src/storage/vocabulary.rs:226` の `compile()` が、登録用語がある場合に次の文を付加する。

> 会議の用語（表記・読みの認識ヒント。無条件な本文置換ではありません）:

その後ろに用語・読み・補足をJSONで連結する。この会議の固定スナップショットでは会議用語が1件有効で、追加ヒント `extraPrompt` は空。問題の説明文を利用者が追加ヒントへ入力したものではない。

`transcription.rs:499` が生成した文字列を `engine.prompt` に設定し、`transcription/whisper.rs:256` がそのまま `--prompt` へ渡す。認識後の本文へ説明文を置換挿入する処理ではない。

同梱のwhisper.cppはv1.9.4、固定commit `927cfce34f31707e17f2bff35c349632fb9e2c3a`。[公式APIの説明](https://github.com/ggml-org/whisper.cpp/blob/927cfce34f31707e17f2bff35c349632fb9e2c3a/include/whisper.h#L523-L530)と同一のローカル固定ソースを確認した。`initial_prompt` はデコーダーのテキスト文脈に入るもので、命令専用の入力欄ではない。実装は初期ヒントを過去文脈へ入れ、認識したトークンも後続の文脈へ保持する。このため、説明文が発話候補となり、生成した反復が後続認識へ影響する機序と整合する。

各120秒区間は同じヒントで新しく認識する。単一の反復が会議全体へ連続伝播したと断定するものではない。区間単位で反復が起きている。

## 同じ実音声での比較

保存済みPCMを一時領域へコピーし、サイズ・SHA256を照合した。実行ファイルとmediumモデルも固定設定のサイズ・SHA256に一致。言語ja、翻訳なし、4スレッド、beam size 5、`--suppress-nst`、VADなしを保持し、プロンプトだけ変更した。保存パラメータの `useGpu=false` に対して `accelerationPolicy=autoMetalV1` が実行時にGPUを有効化するため、元ログと比較実行ログの両方でMetalバックエンドの実使用を確認した。

| unit 0、00:00–02:02 | 元の説明文＋用語JSON | 62 | 保存済みの全文・区間時刻と完全一致して再現 |
| 同上 | 登録用語名だけ | 0 | 別の短文の反復が残る |
| 同上 | 空 | 0 | 同様の反復は解消、19区間を出力 |

| 同上 | 登録用語名だけ | 0 | 別の文の反復が残る |
| 同上 | 空 | 0 | 同様の反復は解消、20区間を出力 |

新たに実行した5件はすべて終了コード0。実行時間は順に20.26秒、15.49秒、15.31秒、22.35秒、11.15秒。別文の反復が残るため、用語名だけの構成も対策完了とは評価しない。ヒントなしの全文正解率や会議全体の品質は未検証。

音声には10秒平均RMSが約−50 dBFSの小音量区間があり、VADも使われていないため、発話が弱い箇所が反復を助長した可能性はある。ただし小音量の因果関係を分離した試験はしておらず、確定原因には含めない。`--suppress-nst` は既に有効であり、今回の通常文の反復を防げていない。

## 対策への示唆

新規認識に渡すヒントから説明・注意書き・JSONの構造を外す必要がある。ただし今回の比較では用語名だけでも反復したため、短縮だけを製品修正として採用せず、反復検知時のヒントなし再認識や発話区間の扱いを実音声で評価する必要がある。認識後に固定文を一括削除すると、反復で失われた発言は復元できない。

保存スナップショットは `whisper-initial-prompt-v1` と実際の文字列・ハッシュを検証している。将来ヒントの構成を変える場合は方式を版管理し、既存ジョブの再開・再試行・復元条件を保持する。既存本文を回復するには修正後の新規認識が必要であり、今回は調査のみとして既存ジョブの実行・公開・本文更新は行っていない。

## 承認された修正

新規ジョブの用語方式を `whisper-vocabulary-v2`、認識ポリシーを `guardedVocabularyV2` とした。用語を `用語（読み）` の改行リストで渡し、見出し・注意書き・JSON・補足を含めない。補足は登録・固定スナップショットに保持し、画面では保存・表示用であることを説明する。追加ヒント、会議別用語の優先順位、8000文字上限は保持する。

新しい `transcription/guard.rs` は本文を変更せず、比較用の正規化を使って、文内反復・隣接する1〜3認識区間の周期反復・長い読みの流入・複数用語の連続転写を検出する。反復単位6文字以上、3回以上、反復全体48文字以上または12秒以上を対象とする。短い相づちを複数区間で束ねて長い反復と誤認しないよう、周期の最小単位も確認する。

問題を検出した処理単位は、同じPCM・モデル・設定でヒントだけ空にして1回再認識する。採用結果・採用モード・検出理由・棄却した初回JSONへの参照をチェックポイントに固定する。再認識も反復する場合は、その単位の完了を保存せず停止する。認識済みの単語を削除する処理はない。`transcription_quality_failed` の表示文言は再起動後もジョブ状態から復元できる。

再開・再試行・最終結果の保存前には、採用JSONと棄却JSONのハッシュ、採用理由の再現性を検査する。バックアップ復元では両JSONの参照を変換し、本文・時刻は保持する。旧方式 `whisper-initial-prompt-v1` と旧ポリシーは元の内容のまま検証・再実行できる。DBのテーブル・公開IPC引数の追加はない。

## 実音声の中間検証と追加修正

分離コピーで実ワーカーを実行し、全19単位の認識と保存まで完了した。全単位のPCM SHA256が元のジョブの入力と一致することを確認した。用語ヒントを維持した19単位の結果では、問題の文は86回から0回、終盤の説明文は4回から0回になった。使用中の会議本文と、コピー内の現在の本文は変更していない。

しかし、ヒントなしの全19単位との追加比較では、unit 3と16で認識時刻の長い空白を伴う欠落が見つかった。最初の全音声検査は欠落の合格条件を満たさず、成功扱いにしていない。実ワーカーは664.86秒、比較認識は計205.39秒。全実行ログでMetalの使用を確認した。

この結果から、反復や読みの転写がなくても、隣接する認識区間の間に12秒以上の時刻空白がある場合は `timestampGap` としてヒントなしで再認識するよう追加した。空白を含む音声を切り捨てる処理や新しいVADモデルの導入はない。再認識結果に残る自然な休止は拒否しない。この判定と、保存される採用理由について合成CLIの結合テストが成功した。

unit 12のヒントなし比較結果自体には長文の反復があり、比較用の正解として使用できない。30秒の中心区間と前後2秒の文脈を使った追加の比較でも冒頭に反復を確認した。反復した比較結果の時刻や文字数を発話量の基準にしないよう、実音声用の検証コードでも比較元の品質を検査する。音声との全文照合や正解率の評価は完了していない。

中間成果物・比較原文・検証コードはリポジトリ外の実音声検証用一時ディレクトリに保持。`worker-spec.json`、`worker-checkpoint.json`、`worker-transcript.json`、`real-comparison.json`、`verification-summary.json` が中間版の結果であり、時刻空白の対策後の最終合格を示すものではない。

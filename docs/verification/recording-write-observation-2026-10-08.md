# 録音中のCAF書込み確認

録音ファイルに存在する完全なPCMフレームと更新時刻を読み取り、マイクとPC音声それぞれの書込み確認を録音画面とミニパネルへ接続した。両入力に1秒以内の書込みがある場合にだけ「この端末に保存中」と表示する。入力レベル・接続・非同期の書込み受付から保存成功を推測せず、停止後の音声確定と電源断耐性は別に扱う。

## 現在の録音と保存先の照合

録音ヘルパーを起動する前に、確認済みの出力先をディレクトリ記述子で固定する。読取りの前後に現在の録音ID・段階・実際の子プロセスの生存を確認し、同じ保存先から `microphone.caf` と `system.caf` だけを開く。パスの要素と葉のリンクをたどらず、保存先の差し替え、共有されたファイル、読取り中のサイズ・時刻変更を確認済みとして表示しない。状態の読取りで音声・manifest・DBを書き換えない。

CAFヘッダーの走査は256チャンク・1MiBまでに限定する。固定レートの非圧縮PCMを確認し、音声データ領域の完全なフレームだけを数える。予約領域や未完の末尾を音声として数えず、通常の最終化済みCAFと、末尾データ領域の長さが未確定のCAFを区別する。未確定長 `-1` の扱いは[AppleのCAF仕様](https://developer.apple.com/library/archive/documentation/MusicAudio/Reference/CAFSpec/CAF_spec/CAF_spec.html)に基づき、再生用の確定・ハッシュ照合処理は緩めない。

同じ録音でファイル実体、作成時刻、PCM形式、編集カウンターが変わった場合や、完全なフレーム数が減った場合は、その読取り所有を無効にする。正常なCAFにある最初の編集カウンター値は受け付けるが、途中の変更は別の書込みとして採用しない。

## 古い書込みと応答遅延の表示

同じフレーム数の再読取りや更新時刻だけの変更では、元の書込みの経過時間を短くしない。新しいAPI応答の版番号だけでも「保存中」に戻さない。画面側でもRPC待ち時間とスリープ中の壁時計の進行を含め、更新が1秒を超えると現在の書込みとして表示しない。

録音IDの変更・停止では表示をクリアし、古い応答で復活させない。不正な録音IDは画面を停止させず、読取りを開始しない。片方だけの書込み、待機、確認できない状態、更新を確認できない状態を別々に示す。ミニパネルには同じ状態処理による短い表示を接続したが、ネイティブの独立ウィンドウでの配置確認は残る。

## 実CAFと先行検査の修正

最初のRustコンパイルは、共通の安全なファイル開きを分離した際に既存テストの旧関数名を残したため失敗した。既存のリンク拒否検査を新しい同等の読取り関数へ接続し、条件を維持した。

最初の実CAF検査では、正常なAVFoundation製CAFの編集カウンター1を拒否した。最初の正常値を受け付け、同じ所有の途中変更を拒否する形へ修正した。修正後は閉じたAVAudioFile製CAFとAVAssetWriter製CAFの両方を、それぞれ4800フレームとして正確に読み取った。

開いたままのAVAudioFileへ4800フレームを渡した別の合成試行では、スナップショットは36864バイトで、4096バイトのヘッダーに続いて4096フレームが存在した。読取り結果も4096で、未反映の704フレームを含めなかった。このスナップショットを閉じたファイル用の4800期待値へ渡した検査は終了コード101となったため、閉じたファイルの成功とは区別する。4096という実在量と不変のファイル内容を検査する専用ケースを追加し、全体検査の終了後にビルド・実行して1件成功した。この4096フレームは今回の合成試行の観測値であり、すべてのOS・入力で同じ内部バッファ量になるとは扱わない。

Swiftの最初の合成実行は既定のモジュールキャッシュへの書込み制限で失敗したため、専用の一時領域を指定して成功した。ブラウザの先行実行は専用セッション未起動の応答で検査前に終了し、開く操作・状態確認・検査を同じ実行環境で行った最終重点検査は成功した。これらの先行失敗ログは残す。

## 残対応

今回の状態は現在のファイルへの書込みの観測であり、音声全体の復号・停止後の確定・物理媒体への永続化・電源断の損失上限を保証しない。実際の録音中のAVAssetWriter、長時間と機器切断、明示スリープ後の欠損・回復、部分CAF救出、Macアプリと三画面の統合、実モデル、配布と先行試用は残る。正式評価・10話者・Windows固有部分は保留し、Windows CIは停止したままとする。

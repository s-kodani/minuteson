# 録音入力履歴のバックアップと追加復元

録音の取得履歴・通知台帳・停止時診断を、実際のバックアップと新IDへの追加復元に接続した。元の録音側の証拠は変更せず、復元先の会議・録音への所属を別の固定記録で保持する。復元後の通知配送と要確認一覧への接続は残る。

## 元録音の取得と実体の照合

終了済みの録音をDBから取得し、Storageが保持する同じルート実体から、会議・audio・録音ディレクトリを記述子相対で開く。別媒体、所有者の不一致、シンボリックリンクを拒否する。履歴と台帳は所有者だけに許可された通常ファイルを必要とし、manifestも所有者と単一リンクを検査する。

取得対象は `input-events.json`、`input-notices.json`、`manifest.json` の3種類に限定する。元のバイト列を容量付きで読み、読込み前後の実体とサイズ・更新情報を照合する。小さな実体情報とSHAを保持し、バックアップ公開前にも親ディレクトリの列とファイルの有無・内容を再検査する。同一バイト列への置換や新しいファイルの出現も変更として扱う。

通知台帳の書込み所有者は取得しない。共有データ保守の排他と読取り専用の照合を使い、既存の書込み所有者を開いたまま元データを取得する。取得後の元ファイル変更をバックアップの成功として採用しない。

## 元の所有と復元先の所属

DB移行29で、終了済みの `recording_sessions` に不変な `input_history_snapshot_json` を追加した。外側には会議IDと録音ID、内側には元録音所有・元履歴・元台帳・古い受付権限を外した通知保持範囲・停止時診断を保持する。移送データの検査は[不変な移送データ](portable-input-snapshot-codec-2026-10-09.md)と同じである。

通常のバックアップでは、論理DBの出力にだけこの記録を収録する。元のライブDBへ書き戻さず、履歴・台帳・manifestも変更しない。復元済みの固定記録がある場合は、元の録音ディレクトリを推測して読まず、その記録を検査して収録する。

追加復元では、元の会議と録音への所属を照合した後、外側の会議ID・録音IDだけを新IDへ対応付ける。取得履歴の所有ID、元の受付・表示確認・終了証拠と通知保持範囲は変更しない。通知受付の権限を作る目的で、新IDの録音ディレクトリや取得履歴を作り直さない。管理音声の復元に必要なディレクトリ配置とは区別し、その存在だけで新しい取得証拠や受付権限を認めない。元の受付世代を復元先の通知受付権限にせず、再バックアップと再復元でも同じ元証拠を保持する。

SQL制約は固定記録の更新・消去と録音中状態への変更、別の所属へのINSERTを拒否する。外部論理DBの読込み、復元構築の封印と公開では、型付き内容と所属を検査する。旧形式20〜28のDBにはこの列を要求せず、移行で履歴や保存成功を作らない。

## 容量と診断

元履歴65KiB、元台帳と通知保持範囲それぞれ128KiB、元manifest256KiBの上限を維持する。内側の不変記録は512KiB、所属付き記録は513KiB、録音は10,000件、記録の総容量は128MiBを上限とする。

音声manifestが管理資産として登録されていない失敗録音も対象に含む。停止時の要求版・確定版・保存結果・終了状態と未確定の診断を残す。端末パスを含む任意のエラー文は持ち運ばず、履歴の欠落を保存成功へ変換しない。

## 検証状況

新規の重点検査は、実際のバックアップ・追加復元・再バックアップ・2回目の追加復元、元DBとファイルの不変、既存会議の保持、元の表示確認の有無、保持不足、停止時の保存失敗を対象にする。実体差替え・リンク・不正な所属・重複項目による公開拒否と、旧DBの移行も対象にする。

最初の重点検査のビルドは、macOS ARM64リンカーの分岐距離上限で失敗した。型検査後のリンク失敗であり、テストは実行されていない。ログは `/private/tmp/mon-input-backup-focus.log` に保持する。

テスト専用のパッケージ最適化による再構築はリンクに成功し、重点5件中4件が成功した。実際のバックアップから2回目の追加復元までの検査も成功したが、SQL制約の検査1件は、検査用会議に録音元の属性がないため既存の制約で拒否された。録音元属性と元の有効な録音設定を検査データへ追加し、製品側の制約は変更していない。この修正前の結果は `/private/tmp/mon-input-backup-focus-optimized.log` に保持する。

旧DBの編集履歴移行検査でも、検査準備が移行28だけを取り除いて移行29を残したため、不連続な移行履歴を拒否して失敗した。旧形式準備の共有ヘルパーで移行29、28の順に取り除くよう検査を修正した。旧DB検査を緩めず、旧28形式の録音・取得履歴・停止時診断を保持する移行の検査も補強した。失敗ログは `/private/tmp/mon-input-backup-legacy-fixture-initial.log` に保持する。

修正後の重点検査は追加のCargo設定引数なしで終了コード0となり、新規5件がすべて成功した。構築は14分16秒、重点検査は12.76秒で、旧28形式の既存録音・取得履歴・停止時診断の不変も確認した。ログと成果物のプロファイルは `/private/tmp/mon-input-backup-focus-final.jsonl` に保持する。

最初の全体 `make check` は終了コード2で、通常Rust1,630件成功・7件失敗・専用60件ignoredとなった。ログは `/private/tmp/mon-input-backup-full-check-final.log` に保持する。失敗は停止時診断のエラー文の期待値1件、旧20・21・26形式を作る検査データの列定義3件、旧27形式から移行した後の版番号の期待値3件である。全体検査はRust通常検査で停止したため、その後の専用連携の合格証拠にはしない。

停止時診断の所有・状態と保存結果の検査を分け、同じ不正結果を従来の結果診断の文で拒否する。拒否条件は変えていない。旧形式の検査では移行29の新しい列だけを除き、残った列を当時の信頼済みスキーマと照合する。論理データの録音行では除くセルがNULLであることを必須とし、同じ位置への再挿入で元の行と完全一致することと、録音行数の一致を確認する。他の行と音声等のペイロードはそのまま保持する。録音行や元証拠は消さず、製品の旧形式検査も緩めない。移行後の版番号は登録済み移行の数に合わせ、元の旧27形式と証拠保持の期待値は維持した。

最初の修正後の再検査では、旧26形式の検査データに録音行が1件あることを構築中に追加確認した。空テーブル専用の準備では不十分なため、同じ検査を明示停止し、上記のNULLセルだけを除く方法へ修正した。この停止した検査のログは `/private/tmp/mon-input-backup-full-check-repaired.log` に保持し、合格やテスト失敗とは扱わない。

録音行を保持する修正後ソースを固定した全体 `make check` は終了コード0で完了した。通常Rust1,637件成功・失敗0件・専用60件ignoredで、新規5件と前回失敗した7件もこの実行に含む。構築は13分53秒、通常Rustの検査は954.31秒だった。Python65件、Swift119件中117件成功・専用2件skip、フロントエンド543件と型検査・ビルド、CAF4800フレームの合成音声読戻しも成功した。後続の専用Swift/Rust連携12件、特徴量ヘルパー9件・親呼び出し1件、保存区間別話者ワーカー6件も成功した。専用検査を通常の件数へ加算せず、60件すべての明示実行とは扱わない。最終ログは `/private/tmp/mon-input-backup-full-check-repaired-v2.log` に保持する。

製品側の `cargo check --locked --offline` も終了コード0で、devプロファイルの型検査が31.11秒で成功した。ログは `/private/tmp/mon-input-backup-production-check-final.log` に保持する。独立検査の `/private/tmp/mon-input-backup-independent-check.log` と、構築前・修正前・明示停止した検査のログも保持し、最終の成功件数へ重複加算しない。

## Rustテストのリンク設定

`app/src-tauri/Cargo.toml` の `profile.test.package.mon-desktop` に最適化レベル1を追加した。巨大なテスト実行ファイルのコードを縮小するための設定で、依存パッケージや製品のdev・release設定を変更しない。既存のテストプロファイルの `debug-assertions = true` と `overflow-checks = true` は維持する。テストの削除・ignored化・失敗の無視は追加しない。

修正後の全体検査と同じ、再構築不要のテスト成果物のCargo JSONでも、最適化レベル1、debuginfo 0、debug_assertionsとoverflow_checksがともにtrueであることを確認した。記録は `/private/tmp/mon-input-backup-repaired-artifact.jsonl` に保持する。Cargoの全体表示は `unoptimized` だが、パッケージ単位の実際の成果物プロファイルとは区別する。テスト実行ファイルは785,235,696バイトで、コードの `__text` は420,689,152バイトだった。これは検査用の成果物であり、製品アプリのサイズ・性能・品質の測定値にはしない。

上記の修正前のリンク成功でも、大きなunwind情報に関する警告は残った。以前の[テスト起動安定性](rust-test-startup-2026-10-06.md)で扱った起動時のESRCHとは別のリンク失敗であり、今回のリンク成功だけで全検査の成功や製品アプリの動作を保証しない。

全検証プロセスの終了と使用中ファイルがないことを確認した後、今回の検査用Rustキャッシュ `/private/tmp/mon-input-backup-native.VkBtdW` の5,648,376KiB（約5.4GiB）を削除した。ソースから再構築できる生成物だけで、ログ・提供音声・モデルは削除対象にしていない。製品の `app/src-tauri/target` は約38MiBと既存releaseを保持し、製品アプリは再構築・起動していない。Windows CIは読み取り専用で `disabled_manually` を確認し、有効化・実行を行っていない。

## 残る接続

復元先が所有する書込み台帳、元証拠と復元先受付の区別、未表示通知と保存診断の一覧、復元先での表示確認後の再バックアップは残る。現時点の保存後通知APIはネイティブ録音ディレクトリを対象にしており、不変な復元記録の存在だけで配送済みとはしない。音声資産が復元済みでディレクトリがある場合にも、取得履歴・診断の読出しと書込み受付を元録音の経路から分ける必要がある。

製品アプリの起動・実録音・Mac実機の通知表示と長時間検証はこの検査の範囲外である。正式評価・10話者・Windows固有部分は保留し、計画全体は進行中を維持する。

# Windows起動連携と確認付き復旧（2026-10-25）

## 起動と復旧

Windows版MON／MON QAで、既存プロセスが残っていても、既存画面の復帰または操作可能な復旧画面に進めるようにした。同一ユーザー・製品識別子・正規化した起動設定フォルダーから連携先を生成する。通常の保存先を開く前に専用ファイルの排他とローカル名前付きパイプを準備し、同時に2つのプロセスが保存先を開かない構造を維持する。

既存MONにはメイン画面のshow／unminimize／focusを要求し、画面側から要求IDに対応した応答を受けてから、新しく開いたプロセスを終了する。接続・応答が5秒以内に確認できない場合は、復旧画面を表示する。旧版についてはWindows Restart Managerで起動設定ファイルの使用者を確認し、同じ実行ファイル・SID・プロセス生成時刻の対象だけに非表示／最小化からの復帰を試す。

復旧画面は「もう一度開く」「MONを再起動して復旧」「起動をやり直す」を提供する。復旧対象が未確認の場合は強制終了の選択肢を出さない。ユーザーが再起動を確認した場合も、実行直前に対象と応答を確認し直す。対象が応答すればその画面を開き、応答しない場合だけ確認したPID・生成時刻のプロセスを終了する。実際のプロセス終了とbootstrapロックの解放を確認する。確認済みトークンは終了開始前に消費し、応答喪失による同じ確認の再送を拒否する。

再起動は確定済み起動状態をその場でリセットせず、新しいプロセスで起動検証全体をやり直す。破損したデータを正常と扱ったり、ロックを削除したり、空の保存先へ自動切替したりしない。権限不正・所有者不明・DB検証失敗の場合も復旧画面を残す。

## 再起動と子プロセスの保護

アプリが属するWindows Job Objectは従来どおりkill-on-closeであり、録音／モデル子プロセスの制限は変更していない。同じジョブ内で再起動先を単純にspawnすると、旧MON終了時に新MONまで終了するため、アプリのジョブ参加前に専用監視プロセスを1つ起動する。

この監視プロセスは保存先・録音・モデルを扱わない。親の実行ファイル・SID・PID・生成時刻を固定し、名前付きパイプのクライアントPIDがその親である場合だけ、一度限りの再起動要求を受け付ける。親の終了を確認してから同じ実行ファイルと起動引数で新MONを起動する。再起動要求がなければ親終了に追従して終了し、親が終了しない場合も10秒で再起動を中止する。

起動準備中の取り込み・テスト初期化・復旧情報取得の失敗は、setupのエラーでアプリ全体を終了させず、起動診断と復旧操作に変換する。外観設定と解析開始の失敗は記録し、アプリの起動を妨げない。録音回収は既存のバックグラウンド処理を維持し、回収できない録音は未完了のまま保持する。

## IPCと互換性

起動連携用にget_startup_instance、acknowledge_startup_activation、open_existing_instance、recover_startup_instance、retry_startupを追加した。起動状態の既存Report形式は変更しない。復旧対象は別のschemaVersion 1のReportで、不透明なtargetId、canRestart、supported、messageとして公開する。

全コマンドをmainウィンドウだけに許可し、再表示・終了・再試行は起動blockedのときだけ受け付ける。パイプ自体は画面表示しか要求できず、プロセスの終了を要求できない。通常画面の保存先検証とコマンド制限は維持する。macOSにはこのWindows向け復旧操作を表示しない。

既存のapp_commands一覧にあったget_meeting_deletion_availabilityの位置も実際のgenerate_handler登録位置に合わせた。コマンドの集合と権限は変更せず、登録一覧の同期検査を通した。

# HRB_202604 の統合停止の調査

## 確認したジョブ

QAデータを一時ディレクトリへコピーし、元のSQLite・WAL・生成成果物は変更せずに調べた。会議IDは `298620fc-de9f-429a-bbc0-15ef3174f5f9`、最新の議事録ジョブは `bdaeb14d-1b0d-4d47-9c73-84665126ff02`。

2026年10月16日00:54:55 JST開始、05:05:50失敗。抽出21・統合20の計41工程中39工程を完了し、40番目の統合（node 39）で停止した。前日のQwen2.5の未完成JSONとは別の失敗である。

固定仕様はQwen3-8B Q4_K_Mの正確なモデルハッシュ・サイズに対応し、`capacity.allocation=modelMaximum`、共有コンテキスト40,960・最大出力32,768・テンプレート予約512だった。プロファイル内の旧値8,192・2,048は新方式の実行予算には使われない。

## 直接の原因

モデル最大出力を毎回予約する方式では、systemとpromptに使える安全側の枠が `40960 - 32768 - 512 = 7680` になる。さらに完結指示と分割余白を確保する。現実装は正確なトークン数ではなく、対応BPEについてUTF-8バイト数をトークン数の上界として使用する。

node 39が受け取った下書きはそれぞれ3,276・6,589 UTF-8バイト。2本を一緒にJSONへ格納するとpromptが9,986バイト、systemが635バイトとなり、この入力枠を超える。そのため2本は別々の統合呼び出しになる。

保存成果物を照合すると、16回すべてで、唯一の入力下書きと出力のMarkdown本文がバイト単位で完全一致していた。長さだけの比較ではない。2本ずつ8巡しても入力が小さくならず、`markdown_plan::Cursor::accept` の上限8巡で、報告された「議事録の統合が入力上限に収束しません」に至った。完了チェックポイントには15呼び出しが残り、16本目の出力はディスクに保存されているが、収束判定で失敗したためチェックポイントには含まれない。

この工程だけで03:12:23から05:05:19まで同じ内容の再生成を繰り返していた。入力欠損・壊れたJSON・モデルのダウンロード失敗による停止ではない。

## 修正の判断点

すでにカタログのコンテキスト上限で実行しているので、「コンテキストを増やす」という案内だけでは解決できない。最大出力は共有コンテキストとは独立に同時確保できる量ではない。

出力の上限値をモデル最大に保ちつつ、長い入力では共有容量の残りまで許可出力を可変にすれば、今回の2本は切り捨てず同じ統合呼び出しへ渡せる。現在の安全側の計数なら、この組み合わせに許可できる出力は `40960 - (635 + 9986 + 512) = 29827` トークンになる。実トークン計数ならさらに余裕がある可能性はあるが、本調査では実トークン数を測定していない。

ユーザーが可変配分への変更を指定したため、新規ジョブに `capacity.allocation=modelAdaptive` を保存する方式を実装した。入力の計画では出力8,192（モデル出力上限がこれより小さい場合はその上限）とテンプレート予約512を確保し、実行時には `min(モデル出力上限, 共有コンテキスト - systemバイト数 - promptバイト数 - 512)` を許可出力とする。出力の最低枠を確保できない入力は分割する。

Qwen3ではsystemとpromptに32,256バイトまで割り当てられ、短い入力は引き続き32,768トークンまで生成できる。Qwen2.5では既存のモデル最大方式と同じ出力8,192・入力24,064となる。いずれも入力分割の余白は別途差し引く。文字数の固定上限は追加しない。

既存の `modelMaximum` と、allocationのない旧プロファイル方式は分割・実行・再開条件を維持する。失敗済みジョブの再試行には旧条件が引き継がれるため、新条件を使うには新しく議事録を生成する。既存ジョブ・元データを後付けで変更しない。

なお、この修正は今回の2本を同じ呼び出しへ渡せるようにするもので、モデル出力がどんな入力でも収束することや、重要事項をすべて保持することを保証する変更ではない。8巡の安全上限や未完成JSONの拒否は引き続き有効。

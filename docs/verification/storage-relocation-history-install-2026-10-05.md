# 保存先移動での履歴台帳配置

2026-10-05に、検証済みの移動先へ、元の保持判断と旧保存先の履歴を保存する内部処理を追加した。台帳へ書き込む前に移動先ファイルの所有を永続化し、中断後は同じ実体にだけコピーし直す。元の構築領域は旧保存先に残し、新しい保存先の回収対象へ取り込まない。保存先切替・旧データ削除・利用者向け操作画面は未接続であり、M3-07は進行中を維持する。

## 移動先の所有確認と配置

会議DBと音声の配置を検証した後、`Placement::install_history`が元の`ControlHandoff`と移動先を再照合する。移動先直下へ新規作成限定で`.mon-handoff.sqlite3`を作り、移動操作、元のmanifest SHA、台帳自身の実体識別子を保存する。既存の空ファイルや所有証拠のない台帳は再初期化しない。

配置先の`.mon-scratch.sqlite3`は、排他的に作成・同期したファイルの識別子を所有台帳へ確定してから本文を書き込む。状態は`pending`、`owned`、`installed`の順に進む。元の制御JSONとSHA、配置する台帳全体のサイズ・SHAも、本文の切り詰めより先に確定する。所有登録前の作成中断で残ったファイルは推測して採用・削除しない。

移動先の所有台帳は形式版1、端末内台帳はmacOSで形式版3、封印する制御JSONは形式版2である。会議用DBの27段階移行とネイティブmanifest形式版1は変更していない。OS設定領域の既存配置台帳の形式も変更していない。

所有台帳はSQLiteのDELETEジャーナルとFULL同期を使用し、ファイルと親フォルダーも同期する。配置操作のOS排他を保持したまま、子台帳のSQLite接続はNORMALロックを使い、コミット後のrollback sidecarを残さない。従来のOS設定・会議データ同居配置でも、元ルート直下の観測対象を途中で増減させないため、子台帳は移動先に置く。

本文の配置後に、実体・サイズ・SHA、台帳のSQL定義・形式版・SQLite整合性、移動先ルート証拠と移動操作、元の履歴・会議DB・音声を照合して`installed`を記録する。これは台帳の配置完了であり、起動設定を新保存先へ切り替える権限ではない。既存の配置状態`ready`も会議DBと音声の検証結果のままである。

## 保持判断と旧保存先の履歴

追加復元の保持確認は、元の確認JSON、SHA、対象intentをそのまま移動先台帳へ保存する。コピーした会議DBの復元操作は変更せず、保持済みの対象を再び回収対象にしない。新しい実体に対する同意を作り直したという意味ではない。

元の構築用一時領域の`areas`・`entries`は、移動先の同名テーブルへ取り込まない。移動先のローカル構築領域は空で開始し、元の構築領域・保持判断・追加復元履歴・直下に残る対象は、旧ルートに属する変更禁止の履歴として別表に保存する。旧実体の所有証拠を新しい実体の削除に使わない。

複数回移動した場合は、以前の各履歴を同じJSON・SHAで保存し、新しい履歴には以前の操作IDとハッシュの参照を付ける。過去の履歴を再帰的にJSONへ埋め込まない。履歴の読出しには件数・容量・参照先の検査があり、旧ルートを開かずに集計できる内部APIを追加した。履歴の画面表示や旧領域の解決・削除操作は未接続である。

既存macOS台帳の形式版2から3への移行は、既知のSQL定義と元ルート証拠を照合してから行う。既存の保持確認や構築領域の記録を維持する。形式版3から履歴表が欠落した台帳を旧形式として採用・再作成することはない。

## 中断後の続行と再送

`owned`で中断した台帳は、記録した同じ実体を確認してコピーし直す。配置済みの台帳は内容を再検査するだけで、再送によって書き換えない。改変、リンク・ハードリンク、実体の差し替え、不正な台帳、未知の追加ファイルでは保持して停止する。

再起動時は旧保存先を開き、現在の会議データと履歴を改めて固定する。配置済みの元履歴が同じで、再起動以降に増えた一時構築記録が有効かつ完全回収済みの場合だけ、既存の完了台帳の再送を認める。新たな未解決領域や保持判断の変更は拒否する。完了後の一時的な構築記録を、既存の移動先履歴へ追加して書き換えない。

## 検証結果

追加Rustテスト12件が成功した。会議DBのバイト保持、正常配置と重複再送、元の保持確認JSONの完全一致、旧構築領域の履歴とローカル回収対象の分離、複数回の内部配置での履歴保持、所有記録後の取消と同じ実体への続行、差し替え・リンク・ハードリンク・台帳改変・未登録作成物の拒否を確認した。既存形式版2の台帳移行と、形式版3の履歴欠落の拒否も検査した。

BootstrapとStorageを閉じて旧保存先から開き直し、途中の台帳の続行と配置済み台帳の無変更再送を確認した。実際の別プロセスを、台帳ファイルの所有登録後で本文を書き始める前と、配置検証・`installed`記録後の2地点でSIGKILLし、再起動後も旧保存先・旧音声を保持したまま続行・再送できることを確認した。子プロセスは終了を待って回収する。この試験は電源断や各トランザクション途中の破損検証ではない。

複数回の移動テストと追加復元保持テストでは、テスト専用の起動設定を使って配置先をStorageとして開いた。製品の保存先切替・ネイティブ操作画面を検証したものではない。従来の共有OS親のモデル・制御ファイルも元の場所に保持され、利用者の録音・設定は移動・削除していない。

最終コードの`make check`は終了コード0で成功した。Python 65件、フロントエンド93件、Swift 9件、Rust通常596件と別実行のAVFoundation製CAF検査1件が成功し、環境依存のRust 11件はignoredだった。型・書式検査とビルドを含む。ログは`/private/tmp/mon-history-install-verified-check.log`、追加テストは`/private/tmp/mon-history-install-complete-focused.log`に保存した。SwiftPMのユーザーキャッシュ権限警告とRustリンク時の既存のunwindテーブル容量警告は残る。

最初の全体検証では、旧形式移行テストの再現データに新しい履歴表が残り、既知の旧形式として拒否された。テストを実際の旧SQL定義へ合わせ、単独の移行検査と全体検証をやり直して成功した。破損した現形式を採用するよう製品の検査を緩めていない。

## 残件と保留

保持未確認の追加復元を新しい実体へ対応付ける内部処理は、後続の[保存先移動後の復元追加物の所有対応](storage-relocation-restore-binding-2026-10-05.md)で追加した。元の会議DBを変えず、元の所有実体と検証済みコピーが一致する対象にだけ対応表を付ける。未登録・不正な対象を新しい回収対象として採用しない。旧保存先に残る構築領域・未知の対象と保持判断の表示・解決は残る。

検証後の起動設定切替とStorageの切替・書込停止の整合、録音・ジョブとの共有操作排他と停止待ち、メイン専用API・フォルダー選択・確認UI、中断配置の明示的な保持・回収、旧データ完全削除は残る。完全削除は別の確認済み操作として実装し、モデル・OS設定・未知の対象を自動で再帰削除しない。

実データ量での性能、悪意ある同一ユーザーの同時改変への完全な耐性、実機WebViewの統合は未検証である。正式評価、10話者、16GB端末での性能評価とWindows固有部分は保留する。Windows CIはGitHub側の無効化とpush・PRトリガーの停止を維持し、ローカルの`make check`を継続する。実装計画全体を完了扱いにしない。

# モデル削除の共有操作制御とAPI接続

2026-10-06に、モデル本体の削除、保存済み条件の続行、変更後の残り範囲への再同意、未開始操作の保持を、共有データ操作コントローラーとメイン画面専用APIへ接続した。確認対象はサーバー内部に保持し、モデル・CPU確認・構成・ジョブ・会議の履歴と端末設定を残す。同意と回復の画面は[画面検証記録](model-body-deletion-ui-2026-10-06.md)で追加した。M3-07全体は未完成である。

## 確認対象とAPI

モデル領域はネイティブ側でアプリデータ領域の `models` に決める。クライアントからモデル領域、削除パス、対象SHA一覧、進捗、保存済み方針を受け取らない。モデル削除の保存記録は、現在の会議ルートとDBの実体、ネイティブモデル領域に結び付けて読み戻す。

| コマンド | 入力 | 用途 |
| --- | --- | --- |
| `review_model_body_deletion` | パッケージIDと配置確認SHA | 新規の対象を確認し、サーバー保持の選択を作る |
| `review_pending_model_deletion` | 保存済み操作ID | 同じ操作を読み戻して残りを検査する |
| `get_model_deletion_paths` | 確認IDと50件単位の位置 | 固定した確認対象を表示する |
| `get_model_deletion_items` | なし | 未完了操作と、読み戻せない操作を区別して表示する |

全コマンドでメイン画面の判定を必須とする。実行・再検査・再同意用確認・保持は既存の `start_data_operation` に接続し、操作トークンと確認ID、操作種別だけを受け取る。旧読み取り専用の対象確認APIは削除許可に変えず、そのまま残す。

確認IDは操作IDと分け、再検査や残り範囲の確認ごとに新しく発行する。50件一覧はサーバー保持の対象から返し、別の確認ID、範囲外や50件単位でない位置、別種別の選択を拒否する。未完了一覧は100件を上限とし、検証できない記録を実行可能な対象へ採用しない。

## 実行と同意

新しい確認範囲に未登録物が含まれる場合、通常の実行を拒否し、未登録物を含める別の明示判断を必須とする。保存済み条件の続行では、その記録の方針を使い、実行要求で方針を変更することはできない。再同意後は最新の固定記録から方針を読み、元の同意の方針で代用しない。

実行直前に固定した対象を再照合する。変更があればファイルを追加採用せず停止し、保存済みの段階と新しい確認IDを返す。取消・失敗後の直接実行は許可せず、明示的な再検査を求める。未開始操作だけを保持・中止でき、開始済みの削除を保持によって復元したことにはしない。

残り範囲への確認は削除も同意保存も行わない。新しい確認IDで別の同意を確定してから続行する。元の同意・対象証拠・過去の処理位置を保持し、完了後の再出現を解決する場合も元のSQL状態は `completed` のまま残す。詳細は[残り範囲への再同意](model-deletion-reconfirmation-2026-10-06.md)を参照。

## 共有実行制御と応答

確認・再検査・再同意用確認・実行・保持に、実際の共有保守leaseを必須とする。録音、取り込み、解析、モデル準備、書き出し、他のデータ操作と同じ開始制御に参加する。終了や取消の要求、画面の切断だけでは実行中のleaseを解放せず、ワーカーの終端状態を公開してから解放する。終了を取り消しても、一度取り消されたleaseは再利用できない。

冷再起動では型付きの同じ操作だけを保守経路から確認し、通常の書込停止を迂回しない。解決後も、保留した通常回復のため再起動が必要な状態を維持する。新規の削除や別操作の開始にはこの例外を使わない。

同一要求の再送は、古い確認IDの検査より先に受理済み要求を照合し、保存済み状態を返す。再検査応答を取りこぼした場合も新しい確認IDを取得できる。完了要求の再送で同意や削除を重ねず、最終確定後の遅い取消では成功結果を取消扱いにしない。本体削除、履歴保持、未開始保持、再起動要否を別の結果項目として返す。

フロントエンドの共有状態検査にモデル削除の種別・進捗・確認・結果を追加した。保存済み方針、対象モデルと操作の同一性、進捗、正確な予約名、ページ位置を検査する。バックアップの画面はモデル削除をバックアップ成功や追加復元として表示しない。

# 復元された録音通知の台帳と再バックアップ

復元先の会議・録音に属する通知台帳をSQLiteへ接続し、元録音の取得証拠を変更せずに通知の受付・実表示確認・終了を保存する。最終の全体検査と製品側型検査は成功し、通知の受付・表示・終了、再起動・持ち運びと会議削除への接続を確認した。Mac実機での表示は残り、計画全体の完了とはしない。

## 元録音と復元先の所有

元のjournal・通知台帳・停止時診断を含む入力履歴スナップショットは不変のまま保持する。通知キューの遷移は元の取得証拠と照合し、受付と終了の所有は復元先録音と照合する。通常録音の台帳は引き続き取得証拠と配送所有の一致を要求し、復元用の分離によって元の拒否条件を緩めない。

DB移行30で、不変な通知移送記録と復元先の書込み台帳を分ける。書込み台帳は元スナップショットのハッシュ・所属・独立した版を検査し、元の遷移順序と保持不足を変更しない。残りの範囲を減らす際には、除いた範囲の末尾の実表示証拠を保持する。表示中の先頭には実際のrender応答の証拠を別に保持し、冷起動で新しい受付期限を作らない。

## 書込みと画面の受付

全ての保存後通知管理処理はStorage内の同じ書込み所有を共有する。最大128所有のLRU管理とDB上の書込み世代を使い、DB所属・不変記録・保存版の差替えを拒否する。同期確定の前に成功応答を返さず、失敗や不確かな保存ではキャッシュを再採用しない。データ保守の共有所有と管理領域の検査は保存前後に行う。保守状態は共有所有とDBロックの待機後にも再確認し、待機中に保守が始まった場合は候補台帳を書き込まない。

保存後通知一覧と受付APIは、復元先のDB台帳を使用する。復元先の音声ディレクトリから録音側の書込み権限を作らない。新しい書込み所有の開始時には古い画面の受付を外し、保存済みの実表示証拠がある先頭は再提示しない。台帳を確認できない場合は元の診断だけを表示し、「復元した通知の受付を確認できません」と案内する。診断表示から通知や受付権限は作らない。

## バックアップと追加復元

書込み台帳とプロセス内の受付時刻は、DBテーブルとして持ち運ばない。バックアップは確定済みの進捗から不変な移送記録を生成し、元DBのスナップショットや移送記録へ書き戻さない。追加復元では外側の会議・録音の所属だけを対応付け、内側の以前の配送所有と実表示証拠は由来として保つ。通知の配送開始前に以前の受付を外す。

進捗は元の保持範囲に対する残りと末尾の表示証拠で表し、以前の移送記録を再帰的に埋め込まない。移送記録は257KiB、書込み状態は256KiB、件数は10,000件、総容量は128MiBを上限とし、個々のDB値はバイト長を調べてから取得する。

会議削除の固定した検査範囲には、復元先の書込み台帳も録音行より前に含める。通知の進捗が確認後に変わった場合は古い削除確認を拒否する。通知台帳があることを対象外の参照として扱って削除を拒否したり、台帳を検査せずに連鎖削除したりしない。旧形式の削除記録は、その版の既知のテーブル構造で検査する。

## 残件

Mac実機での通知表示を残す。合成データの確定直後のSIGKILL検査は、実録音中の中断や電源断の証明にはしない。全検証が終了し、実体・所有と使用中のファイルがないことを確認した後、検証専用`/private/tmp/mon-restored-input-delivery.f5a3le`のRust生成物約3.2GiBを回収した。ログ・音声・モデル・製品target約38MiBと既存releaseは保持した。製品アプリ起動と実録音は行っていない。

通常録音のFLAC保存・独立セグメント・部分救出、実モデル統合、Mac実機・長時間、配布と先行試用を含む計画全体は進行中である。正式評価・10話者評価・Windows固有対応とWindows CIの保留は維持する。

Windows CIはGitHub上で`disabled_manually`を再確認し、ローカルのワークフローは手動起動だけを保持する。有効化・実行は行っていない。

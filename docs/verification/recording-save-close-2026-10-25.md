# 録音保存中の終了確認（2026-10-25）

## 原因と修正

メインウィンドウのネイティブCloseRequestedは、録音のpreparing／recordingだけでなくstopping／savingでも、フロントの終了確認を経由せず直接hideしていた。保存中のウィンドウが消えてもプロセスは終了せず、起動設定のBootstrapLockを保持する。そのため再起動側のtry_lockが拒否される。調査時にもインストール済みMON QAのプロセスが1つ残っていた。読み取り専用で既存ログを確認すると、14:05頃のsavingの後、14:06頃に「原音声セグメントが検証後に変更されました」によるerrorが記録されていた。元音声を保持し次回起動時に再検証する既存エラー処理が動いており、保存成功は確認していない。この保存検証エラーの原因の特定・修正は今回の終了確認とは別であり、検証条件は緩めていない。

- ウィンドウを隠す対象をpreparing／recordingに限定。stopping／savingの×は既存の終了確認へ進む。
- フロントのquit=falseでも保存確認を通し、明示的に選択された場合だけ保存完了を監視する。キャンセル後の自動終了や、停止要求の再送はしない。
- 保存成功のidleを確認するまで終了しない。保存失敗、状態読取りエラー、別セッションへの変更、時間切れは確認画面にエラーを残して終了を止める。
- ネイティブfinish_main_closeも保存中のhideを拒否する。
- 停止・保存を既存の進捗レジストリに公開し、ジョブ一覧と共通進捗に表示する。セッション単位の同じジョブとして扱い、実測のない進捗率は表示しない。永続ジョブテーブルや保存処理本体は変更しない。
- 保存後に解析などが実行中なら、その処理に対する既存の終了確認も継続する。

# 中断したデータ操作の確認と保持

2026-10-05に、構築用コピーと未公開の追加復元データの要確認一覧、明示的な再検査と回収、ファイルを変更しない保持確認を接続した。合成データのネイティブテストと、模擬IPCを使うブラウザ操作を検証した。実機WebViewでの一連の操作やM3-06全体の完了を意味しない。

## 対象と結果の区別

設定画面では、保存ルートと端末内の所有記録にある対象だけを表示する。構築用コピーは`.mon-stage-UUID`、未公開の追加復元は対象会議の`meetings/UUID`に限定する。共有の`meetings`全体を検査せず、名前のパターンで対象を探して登録することもない。利用中のコピー、公開済み会議、保持して確認済みの対象は新しい回収操作に渡さない。

| 選択または結果 | ファイルと確認記録 |
|---|---|
| 対象を確認する | 所有記録と対象のメタデータを読む。回収や保持記録の確定はしない |
| 再検査して回収 | 既存の限定回収を実行する。所有不明のファイルは残し、要確認が残った場合は回収完了と表示しない |
| 保持して確認を完了 | ファイルを変更せず、不変の確認記録を保存する。回収済みや公開済みにはしない |
| 確認を取り消す | 確認だけを破棄する。進行中なら実ワーカーの終了まで保護を維持する |

既存会議、元バックアップ、公開済み音声は操作対象ではない。完全削除や外部バックアップの削除にも該当しない。所有不明のファイルを削除して回収を完了させるUIは提供しない。

## ネイティブ確認と保持の境界

ネイティブ側が保存ルート、対象種別、操作ID、所有記録の意図、状態と対象メタデータの指紋、新しい確認IDを保持する。クライアントから送るのは操作トークン、確認ID、選択した動作だけであり、クライアントのパスで対象を置き換えない。確認後に記録・状態・メタデータが変わった場合、確定前に停止して新しい確認を要求する。

メタデータ検査ではファイル本文を読まず、リンクをたどらない。対象一覧は合計2,000操作、検査パスは200,000件で上限を設ける。親リンクや読取不可などで検査が不完全な場合も、その区別を表示する。保持は未検査の内容を含めて残す判断であり、安全に回収できたという意味ではない。

保持の確認記録は端末内の`.mon-scratch.sqlite3`へ保存する。対象種別・操作ID・意図のSHA、観測のSHA、確認ID、時刻と記録のSHAを照合し、更新・削除トリガーで不変とする。通常破棄と起動時の回収もこの記録を確認する。未公開の追加復元を保持した後は元バッチの公開を拒否し、追加復元を行うなら明示的に新しい操作を選ぶ。

台帳は既知の旧SQL定義と`user_version=0`、元の保存ルート実体の証拠がすべて一致する場合だけ、保持表と`user_version=2`を同じトランザクションで追加する。版2で保持表が欠落した台帳を旧版と誤認して自動修復しない。会議DBの27段階移行とアーカイブ形式版2は変更しない。保持記録や構築用コピーは外部アーカイブへ移送しない。

録音、取り込み、AI処理、モデル準備、書き出し、終了と同じ共有開始排他を使う。別種別の確認を回収へ転用する要求は拒否する。応答が失われた場合、読取ポーリングまたは同一要求の再送で結果を確認し、別の操作へ切り替えない。保持の確定や回収の結果は遅れた取消で消さない。

## 検証した範囲

追加Rustテスト9件では、構築用コピーと実際に記録した未公開の追加復元について、保持後の再起動、未登録物の保持、変更後の確認拒否、明示的な再検査、回収と保持の結果の区別、利用中コピーの除外、確認破棄、旧台帳移行、保持表欠落時の起動拒否、元復元バッチの公開拒否、操作コントローラーの同一要求再送と異種操作拒否を確認した。追加復元のテストでは既存の持ち運び対象DB行を照合し、変更がないことを確認した。テストは専用の一時領域を使い、利用者の録音を削除していない。

ブラウザでは`app/tests/data-save-browser-fixture.js`の模擬IPCと`app/tests/recovery-browser-check.js`を使い、16ケースを確認した。読取専用の確認とEscape、フォーカス復帰、両種別の保持、回収、要確認の残存、古い確認からの再検査、停止待ち、取消と確定の競合、応答・イベント喪失、同一要求での結果確認、未確定要求の取消、一覧失敗、OS保留表示、未保存編集の保持、不一致の結果拒否を含む。応答喪失時の結果確認と取消は確認ダイアログ内からも操作できる。既存のバックアップ・追加復元20ケースも成功した。

確認画面を1200×900と900×650で検査した。スクリーンショットは`output/playwright/recovery/`に保存する。これはブラウザ表示の証拠であり、macOSネイティブWebViewや実IPCの統合証拠ではない。開発用HMR接続のエラーは製品の通信試験とは区別する。

最終コードの`make check`は終了コード0で成功した。Python 65件、フロントエンド93件、Swift 9件、Rust通常517件と別実行のAVFoundation製CAF検査1件が成功し、環境依存のRust 11件はignoredだった。型・書式検査とビルドを含む。ログは`/private/tmp/mon-recovery-final-check.log`、ブラウザ16ケースの結果は`/private/tmp/mon-recovery-browser-final.log`へ保存した。Rustリンク時の既存のunwindテーブル容量警告は残る。

## 未検証事項と保留

台帳の初期化中断や破損で保存先を開けない場合の起動案内は残る。壊れた所有記録を推測して採用したり、保持記録をリセットしたりする機能は追加していない。

実機WebView、電源断、容量不足、長時間操作、他プロセスの同時パス置換は未検証。メタデータ確認と削除を不可分にするOS操作の実証や、手動で台帳を全面改変する攻撃に対する暗号学的保証ではない。利用者の実データに保持・回収を適用した試験も行っていない。

Windowsの所有識別と起動時回収、正式評価、10話者、16GB端末の評価は保留する。Windows CIは`disabled_manually`のまま維持し、ローカルの`make check`だけを実行する。保存先変更、完全削除、共通UIとテーマなどの実装計画の残件は継続する。

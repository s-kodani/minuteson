# 1.0.8 WAV保存統一の実装計画

1.0.8へ、通常録音・音声取り込み・5秒テストの管理音声をWAVへ統一する変更を含める。既に入っている待機メモリと内部ログの性能改善も維持する。本書の方針を実装し、統合検証を進めている。実装済みの保存契約は[録音仕様](../spec/recording.md)と[保存仕様](../spec/storage.md)を参照する。配布候補の確定・公開状況とは分けて扱う。

## 完成形と変更範囲

- Windows・macOSの通常録音は、録音中にマイクとPC音声を合成し、単一の16 kHz・モノラル・PCM16 WAVへ保存する。分割CAF、中間FLAC、停止後の全体ミックスを新規録音から外す。
- 音声取り込みは復号・正規化したPCMから直接WAVを作り、そのWAVを正式音声として確定する。同じPCMの中間WAVと正式WAVを重複作成しない。
- 5秒テストは入力別に短いWAVを作る。マイク・PC音声を個別に聴く現在の操作と、確認終了後の削除を維持する。
- 新規録音の音量は区間ごとの取得入力数で平均する。片入力だけの区間はその音量を維持し、ゼロ値PCMを受信した入力も取得済みとして数える。パケット未受信とは区別する。
- WAV化・移行・更新検証が完了するまで、1.0.8の配布候補を確定しない。

## 過剰な変更を避けるための制約

最終レビューで広げすぎと判断した項目を、以下のように絞る。

| 項目 | 採用する範囲 |
| --- | --- |
| 遅着音声用の救出WAV | 新設しない。既存の保存失敗と確定済み範囲の復旧へ接続する。 |
| 一律4秒の追加整列待ち | 追加しない。連番・処理完了・時計確定・変換器の必要サンプルを確定根拠とする。約4秒は同期保存の間隔として維持する。 |
| FFI ABI v2への一律変更 | 行わない。既存の型・関数・意味を維持し、関数追加で対応する。ABI v1を維持し、生成ヘッダーを更新する。 |
| Windows取得系の全面再設計 | 行わない。取得を塞ぐ機器探索・接続準備と、未読PCMを追い越す確定処理を修正対象とする。機器選択や再接続方針は維持する。 |
| 汎用の保存・移行・ジョブ基盤 | 新設しない。既存の所有検証・ファイル公開・DB確定・復旧・整理処理を再利用する。 |
| 全入口への録音用チェックポイント導入 | 行わない。共通化はPCM変換とWAV処理を中心にし、取り込みと5秒テストは既存の所有・確定・取消・整理の寿命を使う。 |
| 関連するWAV処理の一括変更 | 会議音声で必要な箇所に限定する。登録した声の短いWAVなど、今回変更しない形式へ波及させない。 |

単一追記WAVの中断復旧、RF64への拡張、旧未完了データの救出、両OSと更新の検証は必要な変更として残す。

## 実装方針

### 取得順序と合成

取得、正規化・時刻整列・合成、ディスク保存を別の処理所有者に分ける。既存の独立したワーカーは再利用し、取得コールバックで行うのは検証済みPCMの有限量コピーと連番付与までとする。共通Rustコアへ合成処理を置き、SwiftとC++で異なる合成規則を持たない。

入力ごとの接続世代・連番を管理し、PCMと状態変更を同じ順序で処理する。受理済み、変換済み、合成済み、同期保存済みの範囲を分ける。状態通知・タイマー・保存待ちが未処理音声を追い越して確定範囲を進めない。変換器の未排出末尾とフィルターが必要とするサンプルも計上する。

Windowsでは、機器探索・接続準備が取得を止める箇所を分離する。未読パケットがある間の時刻ベースの確定と、容量圧力だけを理由にした先行確定をなくす。既存のOS取得方式を維持し、GetBuffer／ReleaseBuffer等の取得操作は取得所有者が直列に実行する。

PC音声が届かない期間は、取得キューの排出確認と順序付きの未受信観測を使い、処理待ちPCMが残っていないことを確認する。未受信を取得済み無音の証拠にはしない。OS自体が過去時刻の音声を異常に遅く返すことまで防げるとは扱わない。その場合は既存の異常・保存失敗処理へ接続し、今回の変更で出力済み位置に合わせる新しい時刻補正や別音声の救出方式を追加しない。

現行の取得PCM20秒・16 MiB・4,096パケット、入力ごとの未確定120秒、共有保存待ち16 MiB・4,096ジョブの上限を引き継ぐ。処理中も予算に含め、同期保存の確定後に解放する。上限超過・書込み不能では既存方針に従って確定済み音声を保持する。

### 単一WAVの保存と公開

未知の長さへ追記できるWAVライターと、単一WAV内の確定範囲を検証する記録を実装する。既存の途中WAVライターは再実行時に未完ファイルをゼロ長へ戻すため、録音の追記復旧へそのまま使わない。実体識別、原子的な管理記録の更新、DB公開と整理は既存処理を使う。

音声本体は1ファイルとし、管理記録には所有・時計・ブロックハッシュ・確定フレーム数を保持する。確定順序は「PCM書込み → 同期保存 → 読戻し照合 → 管理記録の同期 → 確定範囲の公開」とする。約4秒間隔の同期保存を維持し、工程ごとの重複した全ファイル走査を増やさない。正常終了では範囲ハッシュの照合と正式ヘッダーを含む全体ハッシュを同じ読取りで計算し、ファイル実体・更新時点を公開まで照合する。中断末尾とヘッダーを修復した場合だけ、修復前の確定PCMに結び付けて再照合する。

長さが未確定の録音WAVはヘッダー領域を80バイト確保し、通常RIFFの予約領域を必要時にRF64のds64へ切り替える。長時間録音のためにPCM本体を移動しない。録音中は保存証拠から確定範囲を検証し、最終ヘッダーの確定後に通常のWAV検査を通す。

停止時は取得・変換の末尾を排出し、ヘッダー確定、形式・全体ハッシュの検証、同一実体のDB登録を行う。録音開始時から最終名`recording.wav`を所有領域内で用い、DBへの原子的な登録を公開境界とする。不要な名前変更は追加しない。既存PCMの全体再変換・再書込みを行わない。正式音声は1トラック・1チャンクとし、入力別の時計・欠損・合成条件を管理記録へ残す。

異常終了後はプロセス終了と所有を確認し、管理記録が証明する範囲だけを救出する。未確定末尾は救出済みと表示せず、取得終了時刻を推測しない。保存ジョブ、通知、再試行、終了待ちは既存の録音セッション単位を継続する。

## 互換性と移行

### 対応する方向と対象

互換性は新版による既存データの継続利用を中心とする。新版から旧版への逆方向は別の条件として扱う。

| 対象 | 1.0.8での扱い |
| --- | --- |
| 1.0.7の完成済み会議WAV | 再生・解析・バックアップを継続する。音声と保存済み解析結果を作り直さない。既存の44バイトRIFFとRF64を引き続き検証する。 |
| 新しい会議WAV | 80バイトの予約領域付きRIFFとRF64を検証する。会議音声のサイズ判定は固定44バイトで計算せず、検証したデータ位置とフレーム数を使う。 |
| 旧未完了録音のCAF・FLAC | 現行の救出アダプターが検証できる形式を、専用の起動時移行で正式WAVへ救出する。分割CAFはmanifest v4、tip v2、entry v2 Float32／v3 PCM16を検証対象とし、連続CAFも現行アダプターの対応範囲に限定する。receipt・時計・ハッシュ、既存のFLAC計画・公開済み出力を照合し、新たな中間FLACは作らない。 |
| 旧未完了取り込み | 現行の旧manifest v2とPCM16 CAFのv3を、既存の取り込み移行を拡張して処理する。正式WAV確定まで元の管理音声を保持する。 |
| 旧5秒テストのCAF | 会議音声への移行は行わない。所有とプロセス・再生の終了を確認し、既存の一時音声整理で回収する。 |
| 会議DB | schema 40へ更新する。既存schema 39のSQLチェックサムと実構造を検証し、取り込み確定トリガーをCAF・WAV両対応へ原子的に更新する。表・列・既存データは維持し、他の過去版の汎用移行は追加しない。 |
| バックアップ | format 8を維持し、旧schema 39のバックアップを新版で復元する。新版の出力はschema 40とし、新版同士で復元できるようにする。format 5／6／7等の受入れは追加しない。 |
| 新版のデータ・バックアップを1.0.7で利用 | 保証対象外。旧版には会議WAVを44バイトヘッダーとしてサイズ判定する箇所がある。新DB schema 40、新しいWAVやmanifestは旧版での読込みを保証しない。 |
| 登録した声の独立WAV | 現行の保存形式と寿命を維持する。会議WAVのヘッダー変更を理由に登録音声の形式・検査条件まで変更しない。 |
| 外部入力ファイル | WAV・MP3・AAC／ALAC M4A・FLACの対応を維持する。外部原本を変更・削除せず、管理用出力をWAVへ統一する。FLAC入力用のデコーダーは保持する。 |
| 設定・AIモデル・編集済み成果 | 保存先、選択中モデル、用語、文字起こし・話者・議事録の人手編集を維持する。形式変更だけを理由に解析・生成を再実行しない。 |
| 通常版・QA版・Store版 | 現行の識別子と保存領域の分離を維持する。異なる版や配布経路で同じDBを同時に利用しない。 |

### 形式版と処理の組合せ

- 録音manifestはv4からv5、新規取り込みmanifestはv3からv4へ更新し、保存音声がWAVであることを明示する。外部原本の情報を示すAudioInfo v1は維持する。
- FFIは既存のABI v1へ関数を追加し、既存の公開型や関数の意味を変更しない。本体と同梱ヘルパーを同じソースから構築する。本体は起動時に要求する保存契約をヘルパーへ渡し、既存の同梱物検証と合わせて不整合を取得開始前に拒否する。出力manifestも検証し、旧ヘルパーへ自動的に切り替える経路を増やさない。
- 新規録音の区間別平均は新しい合成ポリシーとして保存証拠に固定する。完成済み音声は変更せず、旧未完了録音の救出では従来の合成条件を維持する。同じ入力でも旧新ポリシーの出力を同一として再利用しない。
- バックアップの版維持は、持ち運ぶ項目・構造を変えず、読み取るWAVの妥当性検査を広げる範囲に限定する。保存先変更中の未完了WAVに限り、内部の移動管理記録v6で移動前後の所有実体を結び付ける。元の所有予約は書き換えず、所有者・予約ハッシュ・元実体と移動先実体が一致する場合だけ引き継ぐ。既存v3／v4／v5の移動管理記録も継続して受け入れる。新版での旧バックアップ復元と新版同士の往復を受入れ条件にする。

### 移行の実行と失敗時

初回起動で対象領域の形式と移行状態を確認し、旧形式の読出し・変換を専用モジュールに隔離する。アプリの版数だけで判断せず、manifest・保存証拠の版と移行記録で判定する。当該データは移行完了後に通常処理へ渡す。新規・完成済み・移行済みデータは変換をスキップする。旧取り込みを新しいCAFへ変換し直す工程や、途中FLACを完成させ直す工程は追加せず、検証済みの元音声から正式WAVへ進める。

入力証拠、出力実体、移行IDと完了状態を既存の安全な公開処理に結び付け、保存・検証・参照切替後に完了を記録する。中断後は未完了分を再開し、二重登録・二重変換を防ぐ。正常停止と部分救出の終了証拠を混同しない。

旧音声は正式WAVの同期・検証・DB確定後にだけ整理する。移行失敗・非対応形式・所有不一致では元データを保持し、既存の保存再試行・診断へ接続する。空データとして初期化せず、無関係な会議や外部ファイルへ変換・削除を広げない。

移行中に保存先を変更する場合や会議音声を削除する場合も、既存の排他・実体対応・整理台帳を引き継ぐ。旧形式用のコードは専用モジュールと起動時登録へまとめ、将来の対応終了時に通常処理を変更せず切り離せる構造にする。今回、旧形式の対応終了日は新設しない。

### 旧版へ戻す場合

新版で利用した保存領域を1.0.7で開くことは保証しない。旧版へ戻す必要がある場合は、更新前に取得したバックアップを保持し、旧版で使う領域へそのバックアップを復元する。新版利用後の変更を旧版へ持ち帰る自動変換は実装しない。新版のデータを削除・初期化して旧版へ戻す手順は採らない。

既に検証用の旧1.0.8候補を導入した環境は、1.0.7からの通常更新検証と分ける。同じ版数で内容が異なる候補の入替えを、通常の版上げ更新の証拠にしない。

## 実装時に判明した計画の修正

取り込みのDB確定トリガーが`audio/x-caf`だけを認めることを統合テストで確認したため、「DB schema 39を維持する」という当初の前提を修正した。メディア種別を偽装して条件を通す処理は追加せず、schema 39から40への専用移行でトリガー1件だけを更新する。バックアップformat 8の表・列構造は維持し、旧schema 39の読込みを明示的に検証する。

旧schema 39は、macOS配布由来のLFとWindows配布由来のCRLFの2種類について、対応するチェックサムとSQL実構造をそれぞれ検証する。[公式1.0.7ビルド](https://github.com/s-kodani/minuteson/actions/runs/44432938593)のWindows Store配布物を静的に照合し、公開マニフェストと一致するMSIX（SHA256 `3011d170be822c3d04dc0d34db5900220d96fbe3258241b5e81b4e50a6a0618d`）からCRLF版の埋込みを確認した。実行ファイルは起動していない。既知の改行差だけを明示的に扱い、未知のチェックサムやSQL変更は受け入れない。

新規schema 40のビルド元SQLはLFへ固定する。旧Windows DBは既存のSQL実構造を保ち、同じ改行形式のトリガーだけを更新する。移行後も既知の40形式として検証し、削除履歴の照合は元の形式に対応する指紋を維持する。復旧用コピーや初回承認前の保存先移動もこの2形式を検証対象とし、元データや封印済みの配置イメージを検査中に書き換えない。

## 実装順と検証

1. 追記WAVの共通処理と単一ファイルの確定記録を実装し、各確定段階の強制終了・再実行・RIFF／RF64境界を検証する。境界検証には疎ファイル等を使い、大容量の実音声生成を避ける。
2. 両OSの取得順序とライブ合成を接続する。機器探索停止、片入力の処理遅延、未読PCMを追い越す通知、ディスク同期100秒停止、接続世代の交換を注入する。受理済みPCMの欠落・先行確定・追加の時刻補正がないことを確認する。
3. 通常録音の直接公開、取り込み、5秒テスト、専用の旧形式移行を接続する。片入力のみ、受信した無音、PC音声の長時間未受信と再開、欠損区間、正常停止、保存失敗・再試行を確認する。
4. 互換性表の方向ごとに検証する。完成済みWAVの不変、旧CAF／FLAC／取り込みmanifestの救出、移行中断と再開、1.0.7からの更新、バックアップ往復、保存先変更・削除との競合を確認する。合成結果は固定入力を使う参照計算と比較し、旧ポリシーの救出と新規の区間別平均を分ける。
5. 変更箇所のRustテスト、macOSネイティブテスト、Windows CTest、契約整合性と文書検査を実施する。統合後の最終main SHAで既存の全件CI・セキュリティ・両OSの実録音を確認し、待機メモリと内部ログの性能改善も回帰確認する。小さな修正ごとに無関係な検証行列を追加しない。

正常な新規処理でCAF・中間FLAC・重複WAVが作られず、通常録音の末尾排出後に既存PCMの全体再書込みがないことを合格条件とする。未確定の音声を保存済みと表示しない。必要な実機確認が未実施なら、その状態を配布候補の検証結果へ残す。

## 1.0.8の配布候補

性能改善と本変更を含む最終main SHAから、本体・ヘルパー、DMG、更新アーカイブと署名、Windows EXE、MSIX、SBOM、チェックサム、来歴証明を揃える。旧1.0.8候補の実行ファイルと検証結果を、新候補の結果として流用しない。

現行の下書きは既存main候補へ固定されているため、別SHAの添付物へ上書きしない。新候補の検証と同一性確認が完了した後に、旧候補の出自を保持して旧下書きを取り下げ、最終SHAに対応する新しいv1.0.8下書きへ切り替える。公開済みタグ・バイナリは変更しない。

リリースノートと[製品概要](../spec/overview.md#108のリリース準備)を実装・確認状況に合わせて更新し、WAV統一、旧データ移行、区間別音量調整を記載する。録音・保存仕様、関連ガイド、ADRも同じ変更で更新する。現在の「音声の保存形式は変更しない」という説明は実装反映時に改訂する。

検証済み成果物の下書き添付までを準備完了とし、公開とStore送信は[既存の手動手順](../guides/development-workflow.md#releases画面でバージョンタグを管理する)へ引き継ぐ。配布原本と必要な検証証拠は保持し、検証専用アプリ・合成音声・ログ・スクリーンショット・補助スクリプト等は、所有と使用終了を確認して整理する。

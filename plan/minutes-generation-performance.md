# 議事録生成の速度改善計画

作成日: 2026-10-16
更新: 利用者の指定により、生成用の時刻を秒単位にする案を追加
状態: 入力軽量化・工程内表示と8BのMetal対応に続き、利用者の指定で全議事録モデルをGPU自動試行の対象に拡張。実層数の取得・段階的な層数削減を実装し、新方式の32GiB固定条件を撤廃。検証・QAビルドは実施記録を参照。

## 目的と基準

HRB_202604の代表的な抽出工程は現状約13分半〜17分。Qwen3-8B Q4_K_MをCPU 4スレッド・GPUなしで動かし、100発言ごとに約28〜30KBを入力している。以前の同じモデル・CPU設定の測定では約16分のうち約12分が入力評価だった。詳細は [実行中処理の調査](../docs/verification/minutes-generation-runtime-2026-10-16.md) に記録している。

初期の性能目標は、同じ代表区間を現在の約15分から5分以内へ短縮すること。これはGPU等の実測前の目標値であり、達成済みの改善率ではない。会議全体の目標時間は抽出・統合を通した実測後に設定する。

進行中のジョブは現在の固定条件で継続させる。比較試験は現在の推論と競合しない時間帯に、保存入力のコピーと専用の一時領域で行う。

## 実施順序

| 段階 | 内容 | 狙い・判断基準 |
| --- | --- | --- |
| 0 | 入力評価・出力生成・前後処理の計測を分離 | 各施策の実際の短縮量を把握する |
| 1 | 入力JSONの重複を削減 | 品質に必要な情報を残してモデルの入力負荷を下げる |
| 2 | Metal/GPU利用とCPU設定を比較・検証 | 主因である推論計算を高速化する |
| 3 | 工程内の状態と経過時間を表示 | 長い入力評価中も、処理状態を判断できるようにする |
| 4 | 起動・検証・統合の追加最適化を判断 | 改善後の計測で残った大きい負荷に絞る |

## 0. 計測を先に整える

工程ごとに、モデル・実行ファイルの検証、CLI起動、入力評価、本文生成、結果確認・保存の所要時間を分けて記録する。エンジンが返す実トークン数・tokens/sも取得する。現状のログ詳細度2では入力・出力の評価時間が残らないため、利用中の固定バージョンで取得方法を確認する。

診断記録にはモデル・エンジンのハッシュ、デバイス、スレッド数、実行コンテキスト、許可出力上限、入力トークン数、ピークメモリ、スワップの差分を含める。会議本文を性能ログへ複製しない。取得できなかった項目は未取得とし、推測値で埋めない。

比較には同じ保存済み3区間と統合入力を使い、一度に変える条件を一つにする。CPUの現行条件を対照として入力軽量化だけ、GPUだけ、両方の組み合わせを測る。繰り返して測定し、初回の読み込み差、他アプリの負荷、メモリ状態も記録する。最終的にHRB_202604全体で完了時間と品質を確認する。

## 1. 入力JSONを軽量化する

新しいプロンプト版で、各発言から以下の重複を整理する。

- 利用者の指定により、生成用の `audioLink` の表示・URLを両方とも秒単位にする。開始は秒未満を切り下げ、終了は切り上げ、元の発言区間を含む範囲とする。
- `audioLink` に開始・終了時刻が含まれるため、別項目の `start` / `end` を省く。
- `partial=false` は省略できる形式にし、省略時は発言全体であることを指示へ明記する。分割発言の `partial=true` は保持する。
- 本文、話者情報、正確な再生リンク、会議名・開始日時は保持する。

保存済み最初の3区間に対する、推論を伴わない試算は以下のとおり。秒単位化だけで1リンクの4箇所の小数部（各7文字）を省け、100発言あたり追加で2,800 B減らせる。

| 区間 | 現行 | 重複削減のみ | 秒単位化も適用 | 合計削減 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 28,095 B | 21,495 B | 18,695 B | 33.5% |
| 2 | 29,705 B | 23,105 B | 20,305 B | 31.6% |
| 3 | 29,314 B | 22,714 B | 19,914 B | 32.1% |

重複削減だけの案では発言本文・audioLink・話者が全件一致することを確認した。秒単位化を加えた案でも本文・話者は保持し、リンクは元の発言区間を含む秒単位の範囲へ変換する。この比率は入力バイト数であり、トークン数や所要時間の改善率ではない。

例: `00:10:08.800000–00:10:14.200000` は `00:10:08–00:10:15` とする。1秒未満の発言でも終了が開始より後になる。元の録音・文字起こし・内部のマイクロ秒精度は保持し、生成用の参照範囲だけを秒単位にする。録音末尾で切り上げが実音声を超える場合は、再生側で実際の音声終端に収める方式を検証する。

書式チェックはプロンプト版に応じた正規リンクと照合する。既存V1/V2の小数秒リンクを不正扱いにしない。新しい指示文でも「小数秒を省略しない」という旧指示を引き継がず、入力で用意した秒単位のリンクをそのままコピーさせる。

既存のLegacy/V1/V2の生成・再開・復元を保持するため、新形式はV3等の別版として新しいジョブに固定する。入力予算は新しい形式で再計算し、全発言を分割して必ず扱う。最初の比較は100発言上限を保ち、入力形式の変更と分割方針の変更を混ぜない。最大出力の可変配分は維持する。

## 2. GPU利用を検証して導入する

現在の `model_compatibility` はCPU 1スレッド・GPUレイヤー0の試行を成功条件としている。CPUの試行結果をGPU動作の証明に流用せず、デバイス利用の確認を追加する。既存の互換性記録は読み続けられる形式にする。

1. 利用可能なMetalデバイスと、固定エンジンのGPU対応を調べる。
2. 短い完全JSONの生成、キャンセル・子プロセス回収、再起動を確認する。
3. 同じ代表区間でCPUとGPUを比較する。実際にGPUへオフロードされた量もログで確認する。
4. オフロード量を段階的に試し、ピークメモリとスワップ増加を確認する。現在32GBメモリ・約12GBスワップ使用のため、最大量を無条件に選ばない。
5. 新ジョブが推論実行枠を取得した後、最初の抽出前にGPUを短く試行する。成功した実デバイス・オフロード量、またはCPU選択を、完了0工程のチェックポイントへ固定する。これにより試行も既存ジョブと競合せず、再開時は固定済み設定を使用する。

実行中や再開中のジョブを、同じ固定仕様のまま別デバイスへ黙って切り替えない。別マシンへの復元・モデル再結合時にも利用可否を確認する。

CPUを使う場合も4・6・8スレッド等を実測比較する。コア数を増やせば必ず速くなるとは扱わず、入力評価と出力生成それぞれの結果から採用値を決める。

## 3. 工程内の状態を表示する

既存の「完了工程数 / 全工程数」と、それに対応する進捗バーの割合は維持する。追加表示の例は以下。

- `議事録生成 · 解析中 3 / 15`
- `4工程目：入力を解析中 · 経過 5分20秒`
- 本文の出力開始後は `4工程目：本文を生成中`、統合工程では `下書きを統合中`。

エンジンが取得可能な情報に基づいて表示する。入力を読み込む段階のパーセントが取得できなければ、経過時間と処理状態を表示する。CPUが動いているだけで入力解析率を推定したり、時間だけでバーを進めない。

状態通知はジョブID・試行・工程に結び付け、古い通知の混入を防ぐ。工程完了と保存成功は、従来どおり検証済み結果・チェックポイントで確定する。残り時間は同じデバイス・類似サイズの実測が蓄積してから目安として追加する。

## 4. 後続の最適化は効果を測って選ぶ

初期段階ではモデル常駐化、複数区間の並列生成、統合木の変更をまとめて導入しない。現状は入力評価が大きく、これらを一度に変えると品質やメモリへの影響を切り分けにくい。

GPU・入力軽量化後に、次を再測定する。

- モデル検証・初期化・保存の合計が全体の10%以上を占める場合、モデル保持や検証処理の共有化を検討する。変更検知・ハッシュ照合・所有プロセスの回収要件は保持する。
- 統合工程の割合が大きい場合、複数下書きを一緒に統合する案を比較する。全議題と根拠を反映できることを条件とする。
- バイト数による安全側の入力計数が実測上の制約になる場合、固定モデルに対応した正確なトークン計数を検討する。コンテキスト超過を許容する変更にはしない。

## 採用条件

- 入力の全発言本文・話者・根拠への対応を保持する。新方式の秒単位リンクは開始切り下げ・終了切り上げを検査し、旧方式は元の小数秒リンクを保持する。内容の切り捨てや出力上限の引き下げを高速化の手段にしない。
- 見出しの重複、リンクの正確さ、重要議題・決定事項・ToDoの保持を比較する。速くても品質が悪化した案は採用しない。
- 書式不一致は引き続き本文を保存して警告する。最適化の評価では、その警告率も測る。
- 未完成JSONは公開しない。一時停止・再開・再試行・バックアップ復元・人間の編集保持を確認する。
- 短い区間、長い区間、統合、GPUなし、メモリ不足、キャンセル・終了時のケースを検査する。
- 代表区間の比較とHRB_202604全体の完了を確認後、QAアプリを再ビルドして試用する。

実施状況は [V3入力・状態表示の記録](../docs/verification/minutes-generation-performance-2026-10-16.md) と [Metal実装・検証記録](../docs/verification/minutes-metal-acceleration-2026-10-16.md) を参照。32GiB以上のMacと検証した固定Qwen3-8B / llamaエンジンを対象に37/37層のオフロードを採用。全732発言・15工程のCLI完了、生成中の停止と再起動を確認した。追加のモデル保持・検証共有化・統合方式変更は未実施。


追加対応: [全議事録モデルのGPU自動選択](../docs/verification/minutes-auto-gpu-2026-10-16.md)。8Bのハッシュ・固定37層に限定する旧方式は既存ジョブの再開用に保持し、新規生成はモデルごとの実行結果からGPU設定を決定する。
